## 게임 소개

검을 강화한다. 성공하면 단계가 오르고, 실패하면 그대로거나, 떨어지거나, 부서진다.
부서진 검에서 조각을 주워 방지권을 만들고, 그 방지권으로 다음 검을 살린다.
그렇게 +20까지 올리는 것이 목표다.

2000년대 국내 플래시 게임에서 유행했던 "검 강화하기" 장르를 안드로이드로 재해석한 것이다.
게임 시스템의 뼈대(강화 · 방지권 · 줍기 · 조합소)는 그 장르의 관습을 따르되,
코드 · 그래픽 · 사운드 · 밸런스는 전부 새로 만든다.

## 설계 방향

이 프로젝트를 관통하는 원칙 다섯 가지.

### 1. 게임 규칙은 안드로이드를 몰라야 한다

강화 판정 · 확률표 · 경제 · 진행도 규칙을 `:core`라는 **순수 Kotlin 모듈**에 격리한다.
안드로이드 의존성이 들어오면 컴파일이 깨지도록 모듈 자체를 `java-library`로 둔다.

이렇게 하면 두 가지를 얻는다. 게임 규칙을 화면과 무관하게 이해하고 수정할 수 있고,
JVM 단위 테스트가 빠르게 돌아 **10만 판 밸런스 시뮬레이션을 테스트로 돌릴 수 있다.**

### 2. 난수는 주입한다

강화 엔진은 `Random`을 파라미터로 받는다.

```kotlin
fun attempt(state: GameState, items: UsedItems, rng: Random): ForgeResult
```

시드를 고정하면 "이 상태에서 이 난수면 반드시 파괴"를 테스트로 검증할 수 있다.
확률 게임에서 이 장치가 없으면 밸런스 버그를 재현조차 못 한다.
전역 난수를 쓰는 순간 이 게임은 디버깅이 불가능해진다.

### 3. 밸런스는 감이 아니라 시뮬레이션으로 잡는다

확률표를 건드릴 때마다 10만 판을 자동 플레이해서
**평균 도달 단계 · 파산율 · +20 달성률**을 숫자로 확인한다.
"체감상 좀 어려운 것 같은데" 로 조정하지 않는다.
이 시뮬레이션은 튜닝 도구인 동시에 회귀 방지선이다.

### 4. 손맛을 깎는 편의 기능은 넣지 않는다

- 방지권 자동 사용은 **기본 꺼짐**. 설정에서만 켤 수 있다.
  파괴 순간 2.5초 안에 원을 눌러야 하고, 놓치면 검이 날아간다.
  "아 눌렀어야 했는데"가 이 게임의 핵심 감정이다.
- 자동 강화는 **아예 없앴다**(v1.5). 원래도 안전구간에서만 돌아
  긴장이 있는 구간은 손으로 눌러야 했는데, 그렇다면 남는 것은
  "안 위험한 구간을 대신 눌러 주는 버튼" 뿐이라 화면만 차지했다.
- 자리비움 보상은 있지만 **손으로 잡는 편이 훨씬 빠르게** 묶여 있다(1분에 잡몹 한 마리 값).
  꺼 둔 쪽이 이득이면 사냥터가 죽는다.

### 5. 진행이 막히는 상태를 만들지 않는다

골드가 0이 되어도 조각이라는 별도 화폐로 재기할 수 있다.
검 · 골드 · 조각이 전부 바닥나면 골드를 300으로 채워 준다.
검을 사고 되파는 순환은 한 바퀴에 40골드씩 손해이고 구제 상한이 300이므로,
이 장치로 의미 있는 골드를 벌 수는 없다.

## 핵심 시스템

### 강화 판정

```
강화 버튼 → 비용 차감 → 성공 판정
                          ├ 성공 → 단계 +1
                          └ 실패 → 구간별 처리
                                    ├ +1~+5   : 유지 (안전구간)
                                    ├ +6~+12  : 1단계 하락
                                    └ +13~+20 : 파괴 판정 → 파괴 or 하락
```

성공률은 +1의 95%에서 시작해 +20의 2%까지 떨어진다.
파괴 구간에서 실패하면 단계에 따라 40~80% 확률로 파괴된다.

### 모드는 하나 — 무한

난이도 상한이 없다. +20까지는 기준 확률표를 쓰고, **+21부터는 성공률이 직전의 85%씩 줄되
0.5%가 바닥이며 실패는 무조건 파괴 판정**이다.

다만 **계열 검은 +20에서 끝난다.** 그 위는 강화가 아니라 조합으로만 간다
([전설검](#전설검--21부터는-등급이-하나다)).

쉬움 · 일반 · 지옥 세 난이도를 두었다가 없앴다. 모드 선택 화면이 사라지면서
앱을 켜면 곧바로 강화 화면이 되고, "시작까지 길다"는 문제가 같이 풀렸다.

### 담금질 — 실패가 다음 성공률을 올린다

무한 구간은 0.5% 바닥에 붙은 채 **실패가 아무것도 남기지 않았다.** 200번을 실패해도
201번째가 여전히 0.5%라면 그건 긴장이 아니라 대기다.

+21부터는 실패할 때마다 다음 성공률이 오른다. 가산분은 기준 성공률의 **절반**이라
어느 단계에서나 "실패 두 번이면 확률이 두 배"라는 같은 감각이 나온다. 상한은 50%다 —
담금질만으로 공짜가 되면 무한 구간이 이어질 이유가 사라진다. 성공하면 0으로 돌아간다.

시뮬레이션으로 잰 +44 → +45 한 단계: **중앙값 138회 → 23회** (p99 58, 최대 78).
`TemperTempoTest`가 이 구간을 잠근다.

### 축복서와 부적은 하나만

둘 다 켤 수 있으면 "있으면 전부 켠다"가 유일한 최선이 되어 고를 것이 사라진다.

- **행운부적** — 실패해도 안 부서진다. **그런데 담금질은 오른다.** 안전하게 게이지를 쌓는 수
- **축복서** — 이번 판 확률만 +10%p. 게이지가 얕을 때 지르는 수

부적으로 담금질을 쌓다가 게이지가 차면 맨몸으로 지른다. 배타는 `UsedItems`가 지킨다 —
화면이 토글 둘을 각각 다루면 반드시 어긋난다.

확률표에 배수를 곱하는 장치(`Difficulty`)는 코드에 남아 있고 테스트가 그 계산을 지킨다.
게임이 쓰는 것은 무한 하나뿐이다.

### 강화 보너스 — 오래 한 것이 확률이 된다

무한 구간은 맨몸으로 극악이다. +45 성공률이 0.5% 바닥이고 실패는 반드시 파괴다.
담금질로 한 단계 중앙값이 138번에서 23번이 됐지만 그것뿐이었다 — **플레이어가 오래 해서
얻은 것이 강화 확률로 이어지는 길이 없었다.**

네 출처가 **`ForgeBonuses` 한 곳으로** 모인다. 여러 군데서 더하면 왜 이 확률이 나왔는지
아무도 설명 못 하게 된다.

| 출처 | 단위 | 최대 |
|---|---|---|
| 도감 | 10칸마다 +0.1%p | +3.2%p |
| 대장간 스킬 | 레벨당 +0.2%p | +3.0%p (Lv15) |
| 고유검 보유 | 1종당 +0.3%p | +3.0%p (10종) |
| 전설검 착용 | — | +3.0%p |

합계 최대 **+12.2%p**. 파괴방지도 같은 크기로, 파괴 판정이 그 확률로 무효가 된다
(방지권보다 먼저 굴리고 소모품이 아니다).

**시뮬레이터는 이 값을 쓰지 않는다.** 새 세이브는 네 출처가 전부 0이고, 그게
`BalanceSimulation` 이 검증하려는 "맨손 신규 플레이어" 다. 보너스를 시뮬레이터에 넣으면
그 모형이 재려던 것 자체가 흐려진다.

### 도감은 바쳐야 열린다

예전에는 검을 얻으면 저절로 올랐다. 그래서 도감이 **지나간 자취**일 뿐 아무 결정도
요구하지 않았다.

이제 **검을 바쳐야** 칸이 열리고 바친 검은 사라진다. "계속 강화할까, 여기서 도감에
바칠까" 가 매번 선택이 된다. 이미 찬 칸에는 바칠 수 없다 — 헛되이 태우지 않게 막는다.

### 대장간 스킬

골드로 올리는 영구 성장이다(15레벨). 골드는 후반에 쌓이기만 하고 쓸 데가 없었는데
여기가 오래 묶일 곳이 된다.

값을 **지금 강화 비용에 연동**한다. 고정값으로 두면 초반엔 못 사고 후반엔 공짜가 된다 —
강화석이 같은 이유로 같은 방식을 쓴다.

### 계열마다 벼리는 방식이 다르다

계열은 그림과 전투만 갈랐고 **강화대 앞에서는 전부 똑같았다.** 그래서 어떤 계열을
올리든 손에 오는 감각이 같았다.

| 계열 | 벼림 특성 |
|---|---|
| 직검 | 기준. 특별할 것도 모자랄 것도 없다 |
| 곡도 | 성공률 +0.4%p |
| 대검 | 파괴방지 +3%p |
| 세검 | 강화 비용 30% 싸다 |
| 쌍검 | 성공률 +0.3%p · 파괴방지 +1.5%p |
| 마검 | 부서져도 조각을 두 배로 줍는다 |
| 성검 | 축복서가 1.5배로 듣는다 |
| 용검 | 성공률 +0.2%p · 파괴방지 +2%p |
| 낫검 | 도감에 바치면 다음 칸도 함께 열린다 |
| 도끼검 | 강화 비용 20% 싸다 |
| 창검 | 강화석이 2개 덜 든다 |
| 정령검 | 파괴방지 +2.5%p |
| 합검 | 위의 것을 조금씩 전부 |
| 허검 | 실패해도 강화석을 돌려받는다 |
| **전설검** | 성공률 +3%p · 파괴방지 +3%p · 담금질 상한 +20%p |

**직검에는 아무 특전도 없다.** 시뮬레이터가 직검으로만 도는데 값을 주면 그 모형이
재려던 "맨손" 이 맨손이 아니게 된다.

**담금질 관련 특성은 전설검에만 있다.** 담금질은 +21부터 붙는데 계열 검은 +20에서
끝나므로, 계열에 담금질 특성을 주면 영원히 발동하지 않는다. 세검·곡도·정령검에 그렇게
줬다가 전부 다른 것으로 바꿨고 `FamilyForgeEffectTest` 가 같은 실수를 다시 막는다.

### 전설검 — +21부터는 등급이 하나다

예전에는 +21 위에서도 계열이 그대로 따라 올라갔다. 그런데 거기서는 어느 계열이든
하는 일이 같아서, **계열이 열넷이라는 사실이 아무 의미가 없었다.**

이제 계열은 +20이 끝이고, 그 위는 **전설검** 하나다. 가는 길은 조합뿐이다.

```
용검 +20  +  정령검 +20  +  합검 +20  +  허검 +20   →   전설검 +21
```

넷 다 조합으로만 나오는 계열이라, 모았다는 것은 조합 나무를 전부 통달했다는 뜻이 된다.
허검은 회랑 10층 보상에만 묶여 있었는데 **도끼검 + 창검** 조합으로도 얻게 풀었다 —
강화 게임인데 회랑 진도에 강제로 묶이는 것이 전설검 재료로는 너무 높은 문턱이었다.

**전설검은 파괴되지 않는다.** 실패하면 +21로 돌아갈 뿐이다. 재료 넷을 다시 모으는 것은
몇 시간을 지우는 일이라, 그게 걸려 있으면 강화 버튼을 누를 엄두가 안 난다.

**한 번 도감에 바치면 해금이 남는다.** 검은 사라지지만 그 뒤로는 조각 500개로 다시
벼릴 수 있다. 게임에서 가장 높은 벽을 두 번 넘으라고 하면 아무도 두 번째 도전을 하지
않는다.

밸런스 시뮬레이터는 사냥도 조합도 모형화하지 않으므로 이 벽을 넘을 길이 없다.
`BalanceSimulationTest` 는 무한 모드 최고 도달이 **정확히 +20**임을 단언한다 — 21이
나오면 오히려 강화만으로 벽이 뚫렸다는 뜻이다.

### 방지권과 줍기

파괴 판정이 나오면 작은 원이 뜬다. **2.5초** 안에 누르면 방지권을 태워 검을 살린다.
살리지 못했다면 파편이 흩어진다. **3초** 안에 누르면 조각을 회수한다.
조각은 조합소에서 방지권 · 축복서 · 행운부적 · 상위 검으로 바꾼다.

### 무기 — 계열 14종 × 티어 11종

| 계열 | 해금 |
|---|---|
| 직검 · 곡도 · 대검 · 세검 | 기본 |
| 낫검 | +10 달성 |
| 쌍검 | +12 달성 |
| 마검 | 파괴 50회 |
| 성검 | +15 달성 |
| 용검 | +18 달성 |
| 창검 | 줍기 10회 |
| 도끼검 | 파괴 100회 |
| 정령검 | +20 달성 |
| 합검 | 서로 다른 4계열 조합 |
| 허검 | 도끼검 + 창검 조합 · 회랑 10층 |

**이름은 강화 단계마다 다르다.** 같은 이름에 숫자만 붙으면 올라가는 맛이 없어서,
0~20 단계에 각각 고유한 이름을 붙였다.

```
+0 녹슨 쇠칼   +5 예리한 강철검  +10 룬각검          +15 뇌전검
+1 이 빠진 검  +6 은장검         +11 고대 룬검       +16 벼락을 품은 검
+2 벼린 쇠검   +7 은빛 장검      +12 불꽃이 감긴 검  +17 여명검
+3 강철검      +8 세공된 은검    +13 화염검          +18 새벽빛 성검
+4 단단한 강철검 +9 룬이 새겨진 검 +14 용암검         +19 흑룡의 이빨
                                                     +20 흑룡참
```

무한 구간은 다섯 단계마다 바뀐다 — 용린참 → 심연검 → 별을 가른 검 → 이름 없는 검.

화면에는 이름을 크게 띄우고 `+13 · 직검 계열` 을 부제로 작게 붙인다.
**계열은 형태를, 단계는 이름과 그림을 정한다.**

### 그림 — 16비트 픽셀아트

검은 색이 들어간 16비트 픽셀아트 스프라이트다. 48×480 PNG 한 장(7KB)에
**검 30종 × 낡음 3단계 = 90칸**이 들어 있고, 필요한 칸만 잘라 그린다.

- `+0` 은 가장 낡은 칸, `+1~+2` 는 쓴 칸, `+3` 부터 새 칸을 쓴다.
  "녹슨 쇠칼"이 반짝이면 이름과 어긋난다
- 확대할 때 보간을 끈다. 켜 두면 픽셀아트가 흐물흐물해진다
- 계열별로 쓰는 검 종류는 `(인덱스 × 8 + 계열번호) % 30` 으로 뽑는다.
  손으로 고르면 같은 단계에서 계열끼리 그림이 겹친다 — 실제로 겹쳐서 테스트가 잡아냈다

### 화면 — 검보다 앞서지 않는 대장간

강화 화면은 어두운 대장간을 무대로 쓰되 **검 스프라이트 자체에는 손대지 않는다.**
기존의 간결한 정보 배치를 유지한 채 배경의 불빛과 어두운 실내만 더해 검이 중심에
남도록 했다.

- 강화 화면은 스크롤하지 않는다. 재화·검·확률·비용·강화 버튼·하단 메뉴가 한 화면에
  모두 보여야 한다
- 진행 정보가 늘어나는 고단계에서는 검 그림 영역이 먼저 줄어들어 조작부를 밀어내지 않는다
- 강화석 요구나 차단 이유는 강화 버튼 안의 짧은 보조 문구로 보여 중복 줄을 만들지 않는다
- 상점·조합·보관·단련·도감의 기존 배치와 익숙한 아이콘은 그대로 유지한다

### 사냥터 — 10구역

강화가 중심이고 사냥은 그 **돈줄**이다. 검을 들고 몬스터를 탭해서 골드와 조각을 번다.
**더 센 검 = 탭 한 번에 더 크게 깎임** 이 손끝으로 느껴져야 강화할 이유가 생긴다.

| 구역 | 권장 | 잡몹 기준 보상 | 보스 |
|---|---|---|---|
| 초원 | +0 | 14골드 | 들개 우두머리 · 20초 |
| 숲 | +3 | 52골드 | 거대 멧돼지 · 20초 |
| 동굴 | +5 | 120골드 | 굴의 파수꾼 · 20초 |
| 폐광 | +7 | 320골드 | 무너진 갱도의 주인 · 20초 |
| 늪지 | +9 | 760골드 | 늪을 삼킨 것 · 22초 |
| 화산 | +12 | 2,400골드 | 화산의 군주 · 22초 |
| 설원 | +14 | 5,600골드 | 설원의 백룡 · 24초 |
| 용의 둥지 | +16 | 13,000골드 | 늙은 흑룡 · 25초 |
| 심연 | +18 | 32,000골드 | 심연의 왕 · 26초 |
| 무한 회랑 | +20 | 86,000골드 | 회랑 끝의 그림자 · 28초 |

구역마다 **몬스터가 세 종류씩** 나온다 — 흔한 놈 둘, 세고 후한 놈 하나.
그리고 9% 확률로 **희귀 몬스터**가 나온다. 체력은 1.8배지만 보상이 6배라,
탭하다가 이름이 금색으로 뜨면 손이 빨라진다.

잡몹 12마리를 잡으면 보스가 열린다. 보스는 제한 시간이 있어 **공격력이 부족하면
시간 안에 죽지 않는다.** 그것이 "이 보스 잡으려면 +N 은 돼야 한다"는 목표를 만든다.
보스를 잡으면 다음 구역이 열리고, 실패하면 잡몹부터 다시 모아야 한다.

검이 부서지면 사냥도 못 한다. 돈줄이 끊기므로 파괴가 훨씬 무겁고 방지권의 값어치가 오른다.
전투에서는 검이 부서지지 않는다 — 파괴는 강화에서만 일어나야 긴장이 한 곳에 모인다.

**몬스터가 검을 떨어뜨린다.** 잡몹 7%, 희귀 30%, 보스는 반드시.
떨어진 검은 보관함(24칸)에 쌓이고, 조합·재료 강화·판매·분해 어디에든 쓴다.

### 보관함 — 떨어진 검의 쓸모 세 가지

사냥에서 주운 어정쩡한 검이 "팔기밖에 못 하는 짐"이면 드롭이 기쁘지 않다.
세 갈래 쓸모를 만들었다.

1. **조합** — 2~4자루를 녹여 한 자루로. 결과는 재료 중 최고 단계 + (재료 수 − 1),
   계열까지 맞추면 +1 더. 상한 +20 — 무한 구간은 강화로만 간다.
   비용은 재료 중 최고 단계 검 판매가의 절반.
2. **재료 강화** — 강화할 때 보관함의 검을 최대 3자루 태워 성공률을 올린다.
   한 자루당 최대 +6%p, 총 +18%p. 성공하든 실패하든 재료는 사라진다.
   고단계에서 확률을 눈에 보이게 끌어올리는 유일한 수단이다.
3. **판매 / 분해** — 급전이 필요하면 팔고, 조각이 필요하면 분해한다.

### 스타포스 — 별 강화

강화 단계와 **별개의 계층**이다. +10 이상인 검에 별을 최대 5개 붙인다.
별 하나에 공격력 +14%.

- 성공률 80% → 62% → 45% → 30% → 18%
- 실패해도 검은 **절대 부서지지 않는다.** 별이 하나 떨어질 뿐이다
- 비용은 조각 + 골드. 별이 늘수록 급격히 비싸진다

단계는 파괴 위험을 안고 올리고, 별은 파괴 없이 재화를 태워 올린다.
두 계층의 긴장이 겹치지 않게 — 파괴의 공포는 강화 한 곳에만 있어야 무겁다.

### 계열마다 싸우는 방식이 다르다

공격력은 강화 단계에서 나오고, 계열은 그 공격력을 **어떻게 쓰는지**를 정한다.

| 계열 | 특성 |
|---|---|
| 직검 | 기준. 약점도 없다 |
| 곡도 | 연속으로 칠수록 세진다 (최대 +60%) |
| 대검 | 탭 간격이 길지만 한 방이 2.1배 |
| 세검 | 아주 빠르게 칠 수 있고 한 방은 0.6배 |
| 쌍검 | 한 번 탭에 2연타 |
| 마검 | 조각을 1.6배 챙긴다 |
| 성검 | 보스에게 1.6배 |
| 용검 | 화상 — 탭하지 않는 동안에도 1초마다 들어간다 |
| 낫검 | 한 방 1.35배에 콤보도 붙고 조각 1.2배 — 수확하듯 쓸어 담는다 |
| 도끼검 | 가장 느리고 가장 세다. 한 방 2.6배 |
| 창검 | 한 번 탭에 3연격, 보스에게도 소폭 우위 |
| 정령검 | 빠른 손 + 콤보 + 약한 화상. 재주가 많은 대신 한 방은 가볍다 |

### 사운드

짧은 효과음은 **런타임에 파형을 합성한다.** 강화 단계에 따라 음을 올리는 것 같은
변화를 자유롭게 주고, 외부 효과음 파일은 사용하지 않는다.

17가지가 있다(v1.4 기준) — 강화 성공(단계가 높을수록 높은 음) · 유지 · 하락 · 파괴(가장 크고 길게) ·
방지권 사용 · 놓침 · 줍기 · 타격(연속으로 칠수록 음이 오름) · 보스 타격 ·
잡몹 처치 · 구역 클리어 팡파르 · 보스 실패 · 구매 · 이벤트 등장 ·
고유검 탄생(가장 긴 팡파르) · 펫 알 획득 · 회랑 체크포인트.

잡음은 고정 시드로 만든다. 매번 다르면 같은 사건이 다르게 들려 어수선하다.

배경음은 CC0 두 곡이다. 대장간과 메뉴에서는 Ted Kerr의 8비트 곡 **On The Offensive**,
사냥터와 무한 회랑에서는 cynicmusic의 오케스트라 곡 **Battle Theme A**가 이어진다.
앱을 벗어나면 멈추고 돌아오면 같은 지점에서 재개하며, 다른 앱이 소리를 쓰면 Android
오디오 포커스에 따라 멈추거나 음량을 낮춘다. 효과음과 배경음은 설정에서 따로 끌 수 있다.

### 진동

소리는 처음부터 있었는데 진동이 없었다. 폰 게임에서 손맛의 나머지 절반이 여기 있어,
성공도 파괴도 손에는 똑같이 아무것도 오지 않았다.

성공은 짧고 밝게 톡, 유지는 둔탁하게 한 번, 하락은 아래로 미끄러지듯, **파괴는 길게 쿵**.
신기록은 톡·톡·톡 올라간다. 소리를 부르는 자리마다 나란히 붙어서 손과 귀가 같은 말을 한다.

사냥 탭마다는 울리지 않는다 — 연타라 손이 아프고 배터리만 먹는다. 처치와 치명타만이다.
설정에서 끌 수 있고 기본은 켜짐이다.

### 최근 자취와 신기록

결과가 한 번 뜨고 사라져서 "세 판째 말아먹는 중"이라는 이야기가 남지 않았다.
강화 버튼 아래에 최근 12판이 `● · ▽ ✕` 로 남는다. 세이브에도 남긴다 —
앱을 껐다 켰다고 자기 연패가 없던 일이 되면 안 된다.

최고 기록을 넘기면 금색 「★ 최고 기록!」과 전용 팡파르·진동이 붙는다.
+10 위에서만 축하한다. 새 세이브는 처음 열 판이 전부 신기록이라 문턱이 없으면
연출이 금방 값을 잃는다.

### 통계 화면

이 게임에서 가장 신경 쓴 화면.
단계별로 **"표기 40% / 실제 37.2% (241회)"** 를 나란히 보여준다.
강화 게임 플레이어가 늘 품는 확률 조작 의심을 데이터로 직접 해소시키는 것이 목적이다.

### 모듈

```
:core   순수 Kotlin. 안드로이드 의존성 없음. 게임 규칙 전부.
:app    Compose UI · ViewModel · 저장소 구현.
```

### 의존 방향

```
ui (Compose)  →  viewmodel  →  domain (:core)  ←  data
```

역방향 의존은 없다. `data`는 도메인 상태를 직렬화할 뿐 규칙을 갖지 않는다.

### :core 구성

| 파일 | 책임 |
|---|---|
| `GameState.kt` | 한 모드의 전체 상태 (불변 data class) |
| `ForgeEngine.kt` | 강화 1회 판정. 순수 함수, 난수 주입 |
| `RateTable.kt` | 난이도별 · 단계별 확률 데이터 |
| `Economy.kt` | 강화 비용, 판매가, 파산 구제 판정 |
| `Recipes.kt` | 조합소 교환식, 상점 가격 |
| `WeaponCatalog.kt` | 계열 × 티어 정의, 단계 → 티어 매핑 |
| `Progress.kt` | 도감 · 업적 · 칭호 · 통계 누적 규칙 |

### 저장 안전성

자동 저장은 매 강화마다 일어난다. 그래서 중단 타이밍이 많다.

1. 임시 파일에 쓴다
2. 기존 파일을 `.bak`으로 옮긴다
3. 임시 파일을 정식 이름으로 rename 한다

읽기 실패 시 `.bak`으로 폴백하고, 둘 다 깨졌으면 그 파일만 초기화한다.
모드별로 파일이 분리되어 있어 한 모드가 깨져도 나머지와 도감은 살아남는다.

**강제 종료 악용 차단**: 방지권 원이 떠 있는 2.5초 동안 앱을 죽이면
파괴를 무효화할 수 있다. 그래서 판정 결과가 나오는 즉시 "파괴 대기" 상태로 저장하고,
앱을 다시 켜면 파괴 확정으로 처리한다. 방지권 기회는 그 자리에서만 유효하다.
이 처리가 없으면 고단계 구간이 통째로 무의미해진다.

**Compose 화면 자체에는 테스트가 없다.** 시간을 재는 로직을 전부 ViewModel로 빼 둔 덕분에
검증이 필요한 부분은 JVM 테스트로 덮인다. 남은 것은 "그려지는 모양"뿐이라
테스트보다 기기에서 한 번 보는 편이 확실하다.

### 테스트 도구

**`ScriptedRandom`** — 정해 둔 값을 순서대로 돌려주는 난수.
`nextDouble()` 외의 호출은 예외를 던져, 테스트가 의도치 않은 경로를 타면 바로 드러난다.
이것 덕분에 "이 상태에서 난수가 0.9면 반드시 파괴" 같은 확률 분기를 결정적으로 검증할 수 있다.

엔진은 난수 소비 순서를 **계약으로 고정**한다. 첫 번째 `nextDouble()`이 성공 판정,
두 번째가 파괴/하락 판정이다. 행운부적을 쓰면 두 번째를 소비하지 않는다는 것까지 테스트가 잡는다.

"+20과 흑룡참 도감에 닿을 길이 있는가"를 지킨다. 셋 다 콘텐츠가 통째로 사라지는 종류의 실패다.

모드당 2만 판 × 판당 최대 2,000회 시도. 전체 실행에 약 30초 걸리며,
테스트마다 다시 돌리지 않도록 리포트를 캐시한다.

</details>

## 저작권 및 리소스 방침

출시를 염두에 두고 처음부터 안전하게 관리한다.

**사용하지 않는 것**

- 원작 플래시 게임(SWF)에서 추출한 그래픽 · 사운드 · 데이터
- 타사 상용 게임의 무기 이미지 — **변형해서 쓰는 것도 하지 않는다.**
  변형해도 원본을 식별할 수 있으면 2차적저작물로 침해가 된다.

**사용하는 것**

| 리소스 | 출처 | 라이선스 |
|---|---|---|
| 강화검 7계열·전설검·몬스터·전투 효과·배경·UI | 프로젝트 전용 제작 | — |
| 고유검·펫 일부 보조 스프라이트 | Dungeon Crawl 32×32 tiles — David E. Gervais | CC0 |
| 대장간 배경음 | On The Offensive — Ted Kerr (`Wolfgang_`) | CC0 |
| 사냥터 배경음 | Battle Theme A — `cynicmusic` | CC0 |
| 효과음 | 없음 (런타임 합성) | — |

CC0는 표기 의무가 없지만 앱 안 **설정 → 라이선스** 화면에 출처와 링크를 기록했다.
강화검과 몬스터는 게임 전용 원본을 사용하며 타사 상용 게임 이미지는 사용하지 않는다.

"용 모티프 곡선날", "화염 오라", "날개형 코등이" 같은 판타지 무기의 일반적 표현 관습은
특정 주체의 저작물이 아니므로 자유롭게 사용한다.

## 개발 일지

### v0.1.0 — 2026-07-26 · 기획 및 설계 확정

프로젝트 시작. 코드는 아직 없고 설계 문서만 있는 단계.

**결정한 것들**

| 항목 | 결정 | 근거 |
|---|---|---|
| 강화 상한 | 구간형 +20 | 상한이 있어야 "클리어" 감각이 생긴다. 도감 · 수집을 넣으려면 20단계 정도의 여유가 필요했다 |
| 모드 구성 | 난이도 3종 + 무한 | 확률표 한 벌에 배수만 곱하면 되니 구현 비용 대비 수명이 길다 |
| UI 스택 | Jetpack Compose | 화면 7~8개가 전부 "상태 → 화면" 형태이고 연출이 많다. View + XML 대비 배선 코드가 크게 줄어든다 |
| 도메인 격리 | `:core` 별도 Gradle 모듈 | 안드로이드 의존성 유입을 컴파일 단계에서 차단. JVM 테스트가 빨라져 대량 시뮬레이션이 가능해진다 |
| 무기 구조 | 계열 8종 × 티어 11종 = 88종 | 단순 단계별 외형 변화만으로는 수집 콘텐츠가 금방 바닥난다 |
| 계열 선택 | 기본 검 구매 시 직접 선택 | 무작위 배정이면 도감 빈칸을 의도적으로 채울 수 없어 답답하다 |
| 아트 조달 | 벡터 5레이어 조립 + CC0 에셋 | 88종을 통 이미지로 그리면 관리가 불가능하다. 레이어 조립이면 날 실루엣만 늘리면 된다 |

**원작과 의도적으로 다르게 간 부분**

- **모드를 초기화해도 도감 · 업적은 남긴다.**
  수집물이 초기화로 날아가면 아무도 초기화를 누르지 않게 되고,
  그러면 재도전이라는 이 장르의 핵심 재미가 막힌다.
- **자동 강화를 넣지 않는다.**
  전 구간 자동화는 편하지만 게임을 지운다. v1.0에서는 안전구간에만 열어 뒀는데,
  그러고 나니 남는 쓸모가 없어 v1.5에서 통째로 뺐다.
- **불운형 업적을 넣는다.**
  "10연속 실패", "+19에서 파괴" 같은 것들.
  망했을 때도 얻는 게 있어야 다시 시작하게 된다.

**설계 문서 셀프 리뷰에서 잡은 구멍 2건**

문서를 다 쓰고 다시 읽으면서 발견한 것들.

1. **검을 잃은 뒤 새 검의 출처가 문서에 없었다.**
   파괴되면 검이 사라지는데 다음 검을 어떻게 얻는지가 정의되어 있지 않았다.
   무료 지급으로 두면 "파산"이라는 상태가 성립하지 않고,
   파산 구제 조항도 조합소의 `+5 검 교환`도 전부 의미를 잃는다.
   → **기본 검 = 상점 100골드**로 확정하고 파산 구제 조건을 그 가격 기준으로 재정의.
   계열 선택 시점도 이 구매 시점으로 확정.

2. **마검 해금 조건이 존재하지 않는 업적을 참조하고 있었다.**
   해금 조건은 "파괴 50회 업적"인데 업적 목록에는 파괴 100회밖에 없었다.
   → 업적 목록에 파괴 50회 추가.

3. **파산 구제가 무한 루프를 만들 수 있었다.** (구현 계획을 쓰다가 발견)
   구제로 검 한 자루만 주면 골드가 0이라 강화 비용 30조차 못 낸다.
   그렇다고 그 검을 팔면(60골드) 다시 검이 없어져 구제가 재발동한다.
   → 구제 지급을 **검이 아니라 "골드를 300으로 채우기"** 로 변경.
   검은 상점에서 직접 사게 해서 계열 선택권도 지킨다.
   사고 되파는 순환은 한 바퀴에 40골드 손해이고 구제 상한이 300이라 악용 가치가 없다.

그 외 두 가지로 읽힐 수 있던 곳들을 하나로 확정:
축복서 +10%p의 적용 순서(난이도 배수 뒤에 가산, 98% 상한),
비용/판매가 표의 열이 목표 단계인지 보유 단계인지,
자동 강화가 정확히 어느 단계에서 멈추는지(+0~+4에서만 시도).

3~4라운드에서 정책을 아무리 손봐도 나아지지 않은 것이 결정적 단서였다.
플레이어가 못하는 게 아니라 **경제 자체가 자본 축적을 허용하지 않는다**는 뜻이었기 때문이다.

1.75도 비교해 봤다(평균 12.74, 상한 도달률 0.03%). 평균은 더 좋았지만

**시뮬레이션이 잡아낸 경제 설계 결함**

설계 문서는 "판매가 지수(1.6)가 비용 지수(1.45)보다 크니 고단계 도전이 수지가 맞는다"고 적어
두었다. **이 논거가 틀렸다.**

하락 구간에서는 실패가 단계를 깎으므로, 한 단계를 올리는 *기대* 비용에
재시도 횟수(1/p)와 떨어졌다가 되돌아오는 비용이 함께 곱해진다.
원시 비용 지수끼리 비교한 것은 아무 의미가 없었다.

실측하니 +0에서 +10까지의 기대 비용이 약 11,850골드인데 +10 판매가는 6,597골드였다.
한 바퀴마다 5,000골드씩 손해라 **자본 축적이 구조적으로 불가능**했고,
그 결과 가상 플레이어는 파산율 99.7%로 저단계만 맴돌았다. 아무도 +11을 넘지 못했다.

판매가 지수를 1.8로 올려 +10 판매가를 21,423골드로 맞추자 경제가 돌기 시작했고,
위 표의 결과가 나왔다. 회귀 방지를 위해 원시 지수 비교가 아니라
**"기대 비용 대 판매가" 불변식**을 테스트로 고정했다.

시뮬레이션 없이 손으로 맞췄다면 출시 직전까지 몰랐을 결함이다.

**환경 이슈 — 한글 사용자 홈에서 테스트 워커가 죽는 문제**

이 PC의 사용자 홈은 `C:\Users\사용자`로 한글이 들어 있고 Gradle 캐시가 그 아래 있다.
Gradle은 테스트 워커의 클래스패스를 argfile에 써서 `java @argfile`로 넘기는데,
데몬이 UTF-8로 쓰면 java 런처는 그 파일을 네이티브 인코딩(MS949)으로 읽는다.
한글이 든 jar 경로가 전부 깨져 `ClassNotFoundException: GradleWorkerMain`으로 죽었다.

`GRADLE_USER_HOME`이나 `-g`로는 해결되지 않는다. argfile 경로는 `user.home`에서 나오고,
ASCII처럼 보이는 `C:\workAndroid\gradle-user-ascii`는 실제로는 같은 곳을 가리키는 정션이다.
데몬 기본 인코딩을 MS949로 맞추는 것이 해법이었다. 경위는 `gradle.properties` 주석에 남겼다.

### v0.4.0 — 2026-07-26 · M3 방지권 · 줍기 · 강화 연출

손맛을 완성했다. **테스트 155건 통과** (`:core` 145 + `:app` 10), APK 빌드.

**제한 시간 흐름**

```
파괴 판정
  ├ 방지권 있음 → 작은 원 2.5초
  │     ├ 탭    → 검 복구, 방지권 1장 소모
  │     └ 만료  → 소모 없이 기회만 잃고 ↓
  └ 방지권 없음 → 파편 3초
        ├ 탭   → 조각 회수
        └ 만료 → 파괴 확정, 아무것도 못 얻음
```

**시간을 ViewModel이 재는 이유**

Compose의 `LaunchedEffect`로 카운트다운을 돌리지 않았다. 화면이 시간을 재면
재구성될 때마다 타이머가 흔들리고, 무엇보다 **테스트할 수 없다.**

ViewModel로 빼 두니 `StandardTestDispatcher`의 가상 시간으로 검증할 수 있다.
"2.5초 지나면 방지권 창이 닫히고 줍기 창으로 넘어간다"를 **실제로 2.5초 기다리지 않고**
확인한다. 테스트 10건이 전부 즉시 끝난다.

제한 시간 값(2.5초·3초)은 `:core`의 `Timing`에만 둔다. UI 설정이 아니라 게임 규칙이라서다.

**UI에서 지킨 것**

- **방지권 원은 108dp로 작게.** 크고 편한 버튼이면 원작의 긴장이 사라진다.
  테두리 호가 줄어들며 남은 시간을 보여 주고, 35% 아래로 남으면 붉게 바뀐다.
- **파편은 고정 각도로 배치.** 난수로 흩뿌리면 재구성마다 위치가 바뀌어 누를 수 없다.
- **줍기는 넉넉한 영역(190dp).** 놓쳐도 손해일 뿐 파국이 아니라, 여기까지 빡빡하면 짜증만 남는다.
- 창이 열리면 하단 버튼을 감춘다. 원과 파편을 눌러야 하기 때문이다.

**연출**

| 결과 | 연출 | 길이 |
|---|---|---|
| 성공 | 밝은 번쩍임 | 350ms |
| 유지 | 짧은 흔들림 (12px) | 250ms |
| 하락 | 큰 흔들림 (26px) | 400ms |
| 파괴 | 붉은 번쩍임 | 300ms |

하락이 유지보다 크게 흔들려야 손해가 몸에 남는다.
길이를 넘기면 연타로 굴리는 맛이 사라져서 전부 400ms 이내로 묶었다.

**구현 중 잡은 버그**

카운트다운이 매 틱(50ms)마다 화면을 다시 그리는 탓에 **"파괴!!" 배너가 첫 틱에 사라졌다.**
`render()`가 매번 `lastResult = null`로 상태를 만들고 있었기 때문이다.
ViewModel이 `lastResult`를 필드로 들고 있다가 창이 닫힐 때 비우도록 고쳤다.

테스트를 처음 돌렸을 때는 3건이 실패했다. `StandardTestDispatcher`에서는 `launch`가
즉시 실행되지 않아 `forge()` 직후 단계가 아직 `None`이었다. 창을 코루틴 스케줄에 맡기지 않고
**즉시 여는** 것으로 고쳤다 — 한 프레임 늦게 뜨면 그만큼 반응 시간을 빼앗는 셈이라
어차피 이쪽이 맞는 동작이었다.

**실행 미확인**

M2와 같다. 기기도 에뮬레이터도 없어 **앱이 실제로 뜨는지는 확인하지 못했다.**
특히 이번 단계는 눈과 손으로 봐야 하는 것들이라 확인이 더 필요하다.

1. 파괴 시 원이 뜨고 테두리가 실제로 줄어드는지
2. 2.5초가 체감상 적당한지 (너무 짧거나 길지 않은지)
3. 원 크기가 누르기에 적당한지
4. 흔들림·번쩍임이 과하지 않은지

### v0.5.0 — 2026-07-26 · M4 상점 · 조합소 · 모드 4종

경제 루프를 닫았다. **테스트 171건 통과** (`:core` 145 + `:app` 26), APK 빌드.

**루프가 실제로 닫힌 지점**

M3까지 `forge()`는 `UsedItems.NONE`으로만 강화했다. 상점에서 축복서를 팔아도 **쓸 방법이
없었다.** 사는 곳만 있고 쓰는 곳이 없으면 경제가 아니다. 여기서 배선했다.

```
검 판매 · 조각 조합  →  골드 · 조각
                          ↓
                   상점 · 조합소에서 아이템
                          ↓
                   강화에 실제로 사용
                          ↓
                   더 높은 단계 → 더 비싼 검
```

**아이템 토글은 한 번 쓰면 내려간다**

켜 둔 채로 두면 연타할 때 축복서가 순식간에 녹는다. 매번 다시 켜게 했다.
보유량이 0이면 아예 켜지지 않는다. 켜져 있을 때는 표시되는 성공률도 축복서를 반영한 값이다.

**모드 4종**

각 모드는 골드·아이템·기록이 완전히 분리된 독립 세이브다.
모드를 바꾸면 ViewModel을 새로 만들어 분리를 보장한다.

카드에 그 모드의 최고 기록과 보유 골드를 보여 주고, 아직 시작하지 않은 모드는
"새로 시작"으로 구분한다.

**5초 롱프레스 초기화**

원작의 조작을 그대로 가져왔다. 누르는 동안 막대가 차오르고 손을 떼면 즉시 취소된다.
세이브를 지우는 조작이라 일반 버튼으로 만들지 않았다. **초기화해도 도감·업적·통계는 남는다** —
`SaveStore.resetGame`이 그렇게 동작하고 M1 테스트가 지키고 있다.

**화면 전환에 라이브러리를 쓰지 않은 이유**

화면이 넷이고 딥링크가 없다. `difficulty`와 `Overlay` 두 상태면 충분하다.
Navigation Compose를 넣으면 의존성과 개념이 늘 뿐 얻는 게 없다.
뒤로가기는 `BackHandler`로 처리한다 — 오버레이가 열려 있으면 닫고, 아니면 모드 선택으로.

**UI에서 지킨 것**

가격과 교환식을 화면에 다시 쓰지 않는다. 전부 `Economy`·`Recipes`에서 읽는다.
밸런스를 고칠 때 고칠 곳이 두 군데가 되면 반드시 어긋난다.
조합소는 `Recipes.ALL`을 그대로 훑어서, 교환식이 늘어도 화면 코드는 그대로다.

살 수 없는 항목은 비활성으로 두되 **이유를 함께 보여 준다** — "골드가 모자란다",
"검을 들고 있으면 바꿀 수 없다", "조각 N개 부족".

**실행 미확인**

M2·M3과 같다. 기기도 에뮬레이터도 없어 **앱이 실제로 뜨는지 확인하지 못했다.**
이번에 특히 확인이 필요한 것:

1. 모드 선택 → 강화 → 상점 → 뒤로 흐름이 자연스러운지
2. 5초 홀드가 실제로 5초 만에 발동하고 손 떼면 취소되는지
3. 모드를 바꿨을 때 진행이 정말로 분리되는지
4. 축복서를 켜고 강화하면 성공률 표시가 실제로 올라가는지

### v0.7.0 — 2026-07-26 · M6 도감 · 업적 · 통계 · 자동강화 · 설정

스펙의 기능을 전부 채웠다. **테스트 190건 통과** (`:core` 145 + `:app` 45), APK 빌드.

**M1에서 만든 것을 이제야 보여 준다**

도감·업적·칭호·통계 규칙은 M1에서 이미 완성되어 테스트까지 끝나 있었다.
M6는 그것을 화면에 올리는 일이었다. 규칙과 표현을 처음부터 갈라 둔 덕분에
화면 코드에 판정 로직이 하나도 없다 — `Achievement.entries`를 훑고
`Progress`가 계산해 둔 값을 읽을 뿐이다.

**도감 88칸**

얻은 칸은 실제 검을, 못 얻은 칸은 **같은 그림을 어둡게 덮은 실루엣**을 보여 준다.
색을 흉내 내 따로 그리지 않은 이유는, 그래야 실루엣이 실제 검과 정확히 같은 모양이고
나중에 아트를 고쳐도 저절로 따라오기 때문이다.
칸마다 어느 난이도에서 얻었는지 점으로 표시한다.

**통계 — 이 화면의 존재 이유**

맨 위의 **표기 확률 대 실제 확률 비교표**가 전부다.
강화 게임 하는 사람은 늘 "확률 조작 아니냐"고 의심하는데, 그걸 데이터로 확인시켜 준다.

한 가지 조심한 것: **시도가 20회 미만인 단계는 차이를 색으로 강조하지 않는다.**
표본이 적으면 ±20%p쯤은 우연히 나오는데, 그걸 빨갛게 칠하면 없는 조작을 있다고
말하는 셈이 된다. 표기는 지금 모드 기준이고 실제는 전 모드 합산이라는 것도 화면에 적어 뒀다.

**자동강화**

안전구간(+0~+4)에서만 뜬다. 멈춤 판정은 전부 `ForgeEngine.canAutoForge`가 한다 —
화면도 ViewModel도 단계를 직접 비교하지 않는다.
목표에 닿거나, 안전구간을 벗어나거나, 골드가 부족하면 스스로 멈춘다.

`forge()`에서 강화 실행부를 `runAttempt`로 갈라내 손 입력과 자동 루프가 같은 코드를 쓴다.
자동강화는 안전구간에서만 도니 파괴가 나지 않아 창 처리도 필요 없다.

**설정에 없는 것**

효과음 토글을 넣지 않았다. **아직 소리가 없다.** 없는 기능의 스위치를 두면
사용자는 켰는데 아무 일도 안 일어나는 경험을 하게 된다.
데이터 초기화도 넣지 않았다 — 모드 선택 화면의 5초 길게 누르기에 이미 있고,
같은 기능을 두 군데 두면 한쪽만 고치는 날이 온다.

**실행 미확인**

기기도 에뮬레이터도 없어 **이번에도 화면을 눈으로 보지 못했다.**
특히 도감 88칸 격자와 통계 표는 좁은 화면에서 깨지기 쉬운 형태라 확인이 필요하다.

**다음**

M7 — 밸런스 튜닝, 앱 아이콘, 출시 준비. 마지막 단계다.

**가장 컸던 것은 세 번째다.** "잘 만든 게임"의 문법(경제·수집·통계)을 채우느라
원작의 목적성을 죽였다. 사냥이 들어오면서 골드의 출처가 검 판매에서 사냥으로 옮겨갔고,
그때 비로소 **강화 → 더 센 검 → 더 깊은 구역 → 다시 강화** 가 닫혔다.

**아트를 두 번 바꿨다**

처음에는 단색 실루엣 아이콘(벡터 74종)으로 갈았다. 단계마다 그림이 바뀌는 문제는 풀렸지만
납작해 보이는 건 여전했다. 높이를 3등분해 명암을 넣어도 한계가 있었다 —
**단색이라 납작한 것이지 파일 형식 문제가 아니었다.**

그래서 색이 들어간 픽셀아트 스프라이트시트로 다시 바꿨다. 리소스는 300KB → 48KB로 줄었고,
낡음 3단계가 들어 있어 저단계 "녹슨 쇠칼"과 그림이 맞아떨어졌다.

**모드를 하나로 줄였다**

쉬움·일반·지옥을 없애고 무한만 남겼다. 모드 선택 화면이 사라져 앱을 켜면 바로 강화 화면이다.
줄여서 나빠진 게 없고, 오히려 "시작까지 길다"가 같이 해결됐다.

**소리를 파일 없이 만들었다**

`AudioTrack`에 사인파·잡음·주파수 하강을 직접 써 넣는다. 라이선스를 따질 필요가 없고,
강화 성공음의 높이를 단계에 비례해 올리는 것 같은 변화가 공짜로 나온다.

**테스트가 잡아낸 것 (이번 회차)**

| 무엇 | 어떻게 |
|---|---|
| 같은 단계에서 계열끼리 그림이 겹침 | 벡터 배치에서 3건, 스프라이트 배치에서 또 발생. 결국 손으로 고르지 않고 규칙으로 뽑게 바꿨다 |
| 자동강화 종료 조건 오판 | "골드가 부족하면 멈춘다" 단언이 잘못됐다. 루프는 *다음* 비용을 못 낼 때 멈추므로 잔액이 남는다 |
| 제한 시간 창이 한 박자 늦게 열림 | 가상 시간 테스트가 잡았다. 코루틴 스케줄을 기다리지 않고 즉시 열도록 고쳤다 |
| 배너가 첫 틱에 사라짐 | 카운트다운이 50ms마다 화면을 다시 그리면서 결과를 비웠다 |

**남은 것**

- 경제 뒤집기 마무리 — 사냥으로 벌게는 됐지만 검 판매가 아직 상점 앞줄에 있다

### v1.0.0 — 2026-07-26 · M7 출시 준비

M1~M7 완료. **테스트 190건 통과**, 디버그 APK 12MB / 릴리스 APK **959KB**.

**밸런스 재검증**

M4에서 아이템 사용이 배선된 뒤 수치가 바뀌었을 수 있어 다시 측정했다.
결과는 M1 확정값과 동일했다 — 시뮬레이터의 가상 플레이어가 이미 아이템을 쓰고 있었기 때문이다.
확률표를 손대지 않았다.

**릴리스 빌드 — 12MB에서 959KB로**

코드 축소와 리소스 축소를 켰다. 검 그림이 전부 코드라 줄일 리소스가 애초에 적었고,
Compose에서 안 쓰는 부분이 대부분 떨어져 나갔다.

축소기가 `kotlinx-serialization`의 생성 코드를 지우면 **세이브를 못 읽는 앱**이 된다.
도메인 클래스의 `serializer`와 enum 이름을 보존하는 ProGuard 규칙을 넣어 막았다.
enum은 이름으로 직렬화되므로 난독화되면 옛 세이브가 통째로 깨진다.

**서명 키는 저장소에 넣지 않았다**

`keystore.properties`가 있으면 그것으로 서명하고, 없으면 디버그 키로 떨어진다.
빌드가 조용히 실패하는 대신 "빌드는 되지만 올릴 수 없는 APK"가 나오게 한 것이다.
키 만드는 법은 위 [출시 준비](#출시-준비)에 적어 두었다.

**아이콘**

M2에서 급히 만든 도형 아이콘을 흑룡참 티어 색에 맞춰 다시 그렸다.
적응형 아이콘의 안전 영역(가운데 66dp) 안에 검을 담았다.

**스토어 등록에 유리한 점**

권한을 하나도 선언하지 않았고 인터넷도 쓰지 않는다. 수집하는 데이터가 없어
개인정보 처리방침이 단순하다. 외부 이미지·사운드가 없어 라이선스 분쟁 여지도 없다.

**남은 것 — 실기기 확인**

M2부터 M7까지 **한 번도 앱이 실제로 뜨는 것을 보지 못했다.** 기기도 에뮬레이터도 없었다.
빌드가 되고 테스트 190건이 통과한다는 것까지가 확인된 전부다.

기기에 설치해 확인해야 할 것:

| 우선순위 | 확인할 것 |
|---|---|
| 높음 | 앱이 켜지는가. 모드 선택 → 강화 → 상점 → 뒤로 흐름 |
| 높음 | 앱을 완전히 종료했다 켜도 진행이 남는가 |
| 높음 | 파괴 시 방지권 원이 뜨고 2.5초가 체감상 적당한가 |
| 중간 | 도감 88칸 격자와 통계 표가 좁은 화면에서 깨지지 않는가 |
| 중간 | 검 그림이 계열별로 구분되어 보이는가 |
| 중간 | 5초 홀드 초기화가 실제로 5초에 발동하는가 |
| 낮음 | 흔들림·번쩍임이 과하지 않은가 |

확인 후 고칠 곳이 나오면 대부분 한 파일만 손대면 된다.
반응 시간은 `Timing`, 확률은 `RateTable`, 가격은 `Economy`, 검 모양은 `SwordArt`.

### v1.2.0 — 2026-07-27 · 사냥터 10구역 · 계열 12종 · 보관함 · 조합 · 재료 강화 · 스타포스

- 정규식 치환으로 Compose 파일을 고치다 중괄호를 깨뜨렸다. 화면 파일은 통째로 다시 쓰는 편이 싸다.

### v1.4.0-M18 — 2026-07-27 · 강화석과 재료 강화

고단계 강화의 **화폐를 골드에서 재료로 옮겼다.** 테스트 422건 통과.

**문제** — 강화 비용이 전 구간 골드만이었다. 골드는 사냥으로 무한히 벌 수 있어
고단계 강화가 "돈 쌓기"의 반복이 되고, 보관함·분해·사냥이 강화와 끊어져 있었다.

**요구량 표** (목표 단계 기준)

| 구간 | 요구 |
|---|---|
| +0~+12 | 골드만 — 초반 리듬은 건드리지 않는다 |
| +13~+15 | 골드 + 검 1자루 |
| +16~+20 | 골드 + 검 2자루 + 강화석 `3 + (목표-16)` |
| +21~ | 골드 + 검 3자루 + 강화석 `8 + (목표-20)`, 상한 40 |

재료가 없으면 **강화 버튼이 눌리지 않는다.** 성공률 보너스가 아니라 입장료다.
화면은 버튼 위에 「필요 🗡 2자루 🪨 5」를, 아래에 못 하는 이유를 그대로 띄운다.

**강화석** — 조각과 분리된 새 자원이다. 두 자원이 같은 수요를 다투면 어느 쪽도 특별하지 않다.
잡몹 5% · 보스 확정 3~8개(구역 깊이 비례) · 검 분해 시 1~3개 · 조합소에서 조각 20 → 1 교환.

**"성공률 보너스는 추가분에만"** — 기존 재료 강화(성공률 +)는 필수분 위에 얹는 선택으로
역할이 바뀌었다. 필수분에도 보너스를 주면 고단계가 오히려 쉬워지기 때문이다.
필수 2자루 + 추가 3자루를 낮은 단계부터 한 번에 집고, 보너스는 뒤의 3자루만 계산한다.

**시뮬레이터도 재료를 산다** — 밸런스 회귀 테스트가 재료 없이 강화를 돌려 깨졌다.
실제 게임에서는 사냥 드롭으로 얻지만 시뮬레이터는 사냥을 모형화하지 않으므로,
**골드 환산으로 재료를 조달하는 국면**을 넣었다(검 100골드, 강화석 240골드).
골드와 재료가 같은 출처(사냥)라 환산이 타당하다. 그렇게 해도 상한 도달률이 유지됐다 —
재료 비용을 얹어도 경제가 무너지지 않는다는 뜻이다.

### v1.4.0-M19 — 2026-07-27 · 계열 정리와 조합표

**시작은 직검 하나뿐이다.** 계열이 열리는 것 자체가 진행의 이정표가 되고,

| 재료 (계열 집합) | 결과 |
|---|---|
| 직검+직검 | 쌍검 |
| 직검+대검 | 도끼검 |
| 곡도+곡도 | 낫검 |
| 세검+세검 | 창검 |
| 직검+곡도 | 마검 |
| 대검+세검 | 성검 |
| 마검+성검 | 용검 |
| 낫검+창검 | 정령검 |
| 서로 다른 4계열 | 합검 |
| 회랑 10층 | 허검 |

- 조회는 **계열 집합**으로 한다. 직검 2자루든 3자루든 `{직검}` 이라 똑같이 쌍검이고,
  자루 수는 결과 **단계**에만 영향을 준다
- 우선순위: 고유검 레시피 → 조합표 → 기존 일반 규칙
- **조합표는 도감에 공개한다.** 계열을 모으는 길이 보여야 조합소에 갈 이유가 생긴다.

- 상점에는 잠긴 기본 계열의 조건이 「🔒 대검 — 구역 3곳 클리어 (1/3)」처럼 뜬다

### v1.5.0-M25 — 2026-07-28 · 자동강화 제거와 자리비움

**자동강화를 통째로 뺐다.** 원래도 안전구간(+0~+4)에서만 돌았다 —
하락·파괴가 걸린 구간을 자동화하면 게임이 남지 않기 때문이었다. 그런데 그 제약을
지키고 나면 남는 것은 "위험하지 않은 다섯 번을 대신 눌러 주는 버튼" 뿐이고,
그 버튼이 강화 화면에서 한 줄과 목표 칩 다섯 개를 상시로 차지하고 있었다.
쓸모보다 자리값이 컸다.

지운 것은 화면만이 아니다. `ForgeEngine.canAutoForge` 와 `AUTO_FORGE_MAX_LEVEL`,
ViewModel 의 `autoJob` 과 시작·중지, `ForgeUiState` 의 두 필드, 그리고 다른 열두 곳에
붙어 있던 `autoJob != null` 방어 조건까지 함께 사라졌다. **동시에 도는 루프가 하나
줄어든 것**이 실제 이득이다 — 입력 잠금을 놓고 다투는 주체가 줄었다.

지우면서 한 가지를 되살렸다. 자동강화 테스트 파일에는 방지권 자동사용·설정·칭호
테스트도 같이 들어 있어서, 파일을 통째로 지웠다가 되돌리고 자동강화 부분만 도려냈다.
자동강화로 여러 번 굴리던 두 테스트는 **연출 잠금을 직접 풀어 가며 손으로 굴리는**
방식으로 바꿨고(`forgeTimes`), 잠금 자체를 확인하는 테스트를 하나 새로 넣었다.

**자리비움 보상을 넣었다.** 앱을 꺼 둔 사이에도 조금씩 쌓인다. 다만 규칙 하나를
못 박았다 — **손으로 잡는 편이 훨씬 빨라야 한다.** 꺼 둔 쪽이 이득이면 사냥터가 죽는다.

| | 규칙 |
|---|---|
| 기준 | 깬 구역 중 **가장 깊은 곳**. 지금 선 구역으로 하면 못 이기는 구역에 들어가 끄는 것만으로 수익이 오른다 |
| 골드 | 1분에 그 구역 잡몹 **한 마리 값** |
| 강화석 | 한 시간에 1개 |
| 상한 | 8시간. 한 번 복귀로 강화석 8개가 끝이다 |
| 하한 | 2분. 잠깐 나갔다 온 것까지 알릴 필요는 없다 |

보상은 **창을 띄우기 전에 이미 들어가 있다**. "받기"를 눌러야 들어오게 하면 창을
놓쳤을 때 보상이 날아간다. 창은 얼마가 들어왔는지 알리기만 하고, 평소에는 화면을
차지하지 않는다 — 자동강화를 뺀 이유와 같은 이유다.

세이브에 `lastSeenMillis` 가 추가됐다. 기본값 0은 "모른다"는 뜻이고, 그때는 보상을
주지 않는다. 이 필드가 없던 옛 세이브가 0으로 읽히는데, 그걸 "오래 비웠다"로 읽으면
켜자마자 8시간치가 공짜로 들어오기 때문이다. 저장할 때마다 시각을 새로 찍고,
보상을 넣은 직후 곧바로 저장한다 — 넣어 놓고 저장을 미루면 앱이 죽었을 때
같은 시간을 두 번 받는다.

시계는 밖에서 넣는다(`now: () -> Long`). 테스트가 8시간을 실제로 기다릴 수는 없고,
여기서 지켜야 할 것은 **같은 시간을 두 번 받지 않는다**이기 때문이다.
기기 시계를 되돌린 경우는 경과 0으로, 앞당긴 경우는 8시간 상한이 막는다.

도움말에도 열 번째 꼭지 **자리비움**이 붙었다. 다른 꼭지와 마찬가지로 숫자는
`IdleRewards` 상수에서 읽어 온다.

### v1.5.1 — 2026-07-28 · +13 이상 강화가 죽던 버그

**실기기에서 강화를 누르면 앱이 튕겼다.** v1.4의 재료 요구가 들어온 뒤로
+13 이상 전 구간이 그랬는데, 여태 아무 테스트도 잡지 못했다.

원인은 **입장료를 두 번 받은 것**이다. 강화는 재료를 판정 **전에** 태운다
(성패와 무관하게 소모되는 게 규칙이므로 순서가 그렇다). 그런데 판정 함수가
그 안에서 `canAttempt` 를 다시 확인했고, `canAttempt` 는 `ForgeCost.canPay`,
즉 재료 검·강화석 보유량을 포함한다. 이미 태운 재료를 또 요구한 셈이라

> 재료를 딱 필요한 만큼만 가진 플레이어 → 전부 태움 → 보관함 0 →
> "재료 검 1자루가 필요하다" → `check` 실패 → 크래시

가 됐다. 여유분이 있으면 통과하니 **정확히 맞춰 온 사람만** 죽는다.

전제 조건을 둘로 갈랐다.

| | 무엇을 묻는가 | 누가 쓰는가 |
|---|---|---|
| `canAttempt` | 강화를 **시작**할 수 있는가 (골드 + 재료) | 화면·ViewModel의 관문 |
| `canRoll` | 주사위를 **굴릴** 수 있는가 (검·파괴대기·상한·아이템·골드) | 판정 함수의 전제 |

재료는 입장료고, 입장료는 한 번만 받는다.

**왜 테스트가 못 잡았나** — 고단계를 다루는 기존 테스트들이 하나같이
`storage = List(4)`, `forgeStones = 100` 처럼 재료를 넉넉히 채워 두고 있었다.
그 클래스들의 관심사는 파괴·하락 판정이라 재료는 "그냥 통과시키려고" 넣은 값이었는데,
그 여유분이 정확히 이 버그를 가리고 있었다. 새 테스트는 **한 자루도 남기지 않고**
+13부터 +25까지 전 구간을 훑는다.

**초기화 버그도 함께** — 초기화하면 골드 0에 검도 없어 아무것도 못 하는 판이 됐다.
`resetProgress` 가 `loadAndRepair` 를 건너뛰고 세이브를 직접 읽어서 파산 구제가
걸리지 않았기 때문이다. 새로 깐 앱과 똑같은 길을 타게 했다.

### v2.5.0 — 2026-08-08 ~ 08-09 · 용검이 +1부터 시작한다

실기기 플레이 피드백을 연달아 반영한 구간이다. **하나의 설계 변경이 코드
곳곳의 낡은 전제를 드러낸 기록**이라, 이어서 작업할 때 참고가 된다.

**용검이 +1부터다.** 전에는 조합하는 순간 곧장 +21(전설)이었다. 용검은 이미
14계열 중 하나로 전투 스타일·강화 특성·도감 아트를 전부 갖추고 있었는데
`LegendForge.craft()`가 결과를 +21로 박아서 **그 아래(+1~+20)가 만들어질 길이
없었을 뿐**이었다. 이제 마검·성검처럼 +1에서 시작해 +20까지 오르고, +21을
넘으면 전설이 된다. 용검만은 +20 벽이 없다(`LegendForge.canForge`).

이 하나가 드러낸 낡은 전제들:

| 곳 | 무엇이 어긋났나 |
|---|---|
| `ForgeScreen` | +20이면 강화 버튼을 안내문으로 갈아 끼워 **용검이 갇혔다.** 화면이 판정과 다른 조건을 따로 적고 있었다 |
| `Fusion.meltable` | `!isLegend()`만 봐서 +20 이하 용검이 **조합 재료로 선택 가능**해졌다 |
| `Storage.canScrap` | 같은 이유로 **+20 용검을 조각 42개에 부술 수 있었다** (다시 벼리는 데 500개) |
| `Recipes` | 여기만 `legendReached`를 봐서, 용검을 쥔 뒤 +21 전까지는 상점 목록에 뜨는데 사면 거절당했다 |
| `StarForce` | 문서엔 "용검부터"인데 코드는 +21을 쟀다. 별을 잠갔던 이유 둘이 용검엔 둘 다 해당하지 않는다 |
| 도감 | 조합검의 **+0 칸이 영원히 못 채우는 칸**이 됐다(조합이 +1을 내놓고, +1~+5는 안전구간이라 하락으로도 못 닿는다) |

> **여기서 얻은 규칙: 화면은 판정과 같은 함수를 봐야 한다.** 조건을 두 군데
> 적으면 반드시 어긋나고, 그 어긋남은 "버튼이 아예 없다" 같은 형태로 나타난다.

**시즌2가 용검 획득 시점으로 당겨졌다.** +21을 밟아야 열리던 것을 용검을 쥐는
순간으로 바꿨다 — 조합이라는 큰 산을 넘고도 보상이 스무 판 뒤에 오면 넘은
값을 못 느낀다. 사냥터만 따로 열지 않았다: 사냥이 벌어다 주는 강화석이 지갑에
안 보이면 번 것이 어디로 갔는지 알 수 없다. 경계는 `Unlocks.deepUnlocked`
하나다. **한 번 열리면 닫히지 않는다**(`GameState.dragonForged`) — 그 검을 팔면
사냥터가 잠기던 구멍을 막았다.

**파괴 확률을 낮췄다.** +21 이상이 `destroyChance = 1.00`이었다. 실패가 곧
파괴라 화면에 **91~96%**가 찍혔고, 되돌아가는 자리가 +21이나 +1이라 한 번
미끄러지면 스무 단계가 통째로 날아갔다. 조합검·전설검은 방지권도 붙지 않아
**막을 방법 자체가 없는 구간**이었다.

| 목표 | 전 | 후 | 화면 파괴% |
|---|---|---|---|
| +16~18 | 0.20 | 0.14 | 15~17% → 10.6~11.7% |
| +19~20 | 0.275 | 0.18 | 24~25% → 15.6~16.2% |
| +21~30 | 1.00 | 0.22 | 91~95% → 20.1~20.9% |
| +31~40 | 1.00 | 0.28 | 95~96.5% → 26.7~27.0% |
| +41+ | 1.00 | 0.35 | 96.5% → 33.8% |

이제 무한 구간의 실패도 대부분 한 단계 하락이다. 덤으로 **행운부적이 무한
구간에서 처음으로 값을 한다** — 붙들 하락이 생겼다.

**부서졌지만 사라지지 않은 검도 파편을 준다.** 마검·성검·용검은 파괴 판정에
걸려도 바닥으로 떨어지기만 하고 아무 창도 뜨지 않아, 잃은 단계만큼의 파편이
그냥 사라졌다. 직검이 부서질 때와 다르게 취급할 이유가 없다. 이제 같은
파괴창이 뜨고 **방지권만 잠긴다** — 되살릴 검이 이미 손에 있어서지 파편까지
못 준다는 뜻이 아니었다.

**사냥터 수치를 되돌렸다.** v1.6에서 24구역 전부를 권장 단계 +15만큼 밀어
올렸는데("사냥은 용검(+21) 뒤에 열린다"는 전제), 용검이 +1부터고 사냥터도 그
시점에 열리게 되면서 전제가 사라졌다. 갓 조합한 용검으로는 첫 구역조차
버거웠다. 권장 단계·체력·골드를 그 커밋 직전 값으로 되돌렸다 — 체력만
되돌리면 잡몹이 400배 약해진 채 보상은 그대로라 수입이 폭주한다.

그 밖에: 고유검이 재료 계열(마검·성검…)로 표시되던 것 정정, 시즌1 고유검
셋을 전투 능력에서 **소유만으로 오르는 강화 성공률**로 교체(시즌1은 사냥터가
잠겨 있어 전투 능력이 죽은 값이었다), 단련 값 인상(2,000→5,000, 배수
1.5→1.6), 가방에서 고유검의 +N 표시 제거.

### v2.6.0 — 2026-08-10 · 대장간 배경과 한 화면 강화

사용하므로 진행 정보와 사냥터가 열리는 +16 상태에서도 재화부터 강화 버튼, 다섯 메뉴까지
한 화면에 남는다.

소모품 토글 위의 반복 설명은 덜어 고단계에서도 하단 메뉴가 잘리지 않게 했다.

**검과 기존 UI 보존.** 검 스프라이트, 확률과 비용 표시, 상점·조합·보관·단련·도감의
기존 아이콘과 배치는 바꾸지 않았다. 새 배경은 낮은 투명도로 깔고 위아래를 어둡게 눌러
검과 글자의 대비를 유지한다.

**실기기 확인.** `SM_A165N` 1080×2340 화면에서 +0과 +16 상태를 확인했다. +16에서
사냥터까지 열린 상태도 하단 메뉴가 모두 보였고, 위로 스와이프한 전후의 앱 영역 픽셀이

**전투 화면 통일.** 사냥 전투의 구역색 전체 배경과 둥근 HP 바를 제거했다. 대장간 배경 위에

공유한다.

**시즌1 정리.** 용검 전에 열리지 않는 특수강화 패널과 강화석·사냥·스킬·회랑·펫·정수
도움말을 숨겼다. 기록 메뉴 설명과 자리비움 문구, 설정의 효과음·진동·초기화 설명도 시즌1의

### v2.9.1 — 2026-08-12 · 재설계가 떨어뜨린 것을 줍는다

UI 개편 전체를 다시 훑었다. 시각적으로는 완성돼 있었지만 **화면을 새로 짜는 과정에서
호출이 떨어져 나간 장치 둘**이 있었다 — 정의는 그대로 남아 있어 컴파일도 테스트도
통과했기 때문에 아무도 몰랐다.

| 무엇 | 왜 문제인가 |
|---|---|
| **담금질 게이지** | 무한 구간에서 **실패가 눈에 보이는 무언가를 남기는 유일한 자리**다. 이게 없으면 +21 위의 연패가 그냥 손해로만 읽힌다 |
| **쌓은 보너스 합계 줄** | 도감을 채우고 스킬을 올릴 때 **이 줄이 자라는 것이 보여야** 올릴 이유가 생긴다 |

> 죽은 코드는 컴파일러가 잡지만 **죽은 호출은 아무도 안 잡는다.** 화면을 통째로 다시
> 짤 때는 지우려던 것과 딸려 나간 것을 구분해야 한다.

나머지 둘은 화면이 같은 값을 두 번 말하던 것이다. 확률 칸이 큰 글씨로 "20%"를 띄우고
그 아래 라벨에 "성공 20%"를 또 적어 같은 수가 두 번 보였고(숫자는 위, 이름은 아래
한 번씩으로), 보관함은 바로 위 지갑 줄이 이미 보여 준 골드를 한 줄 더 적고 있었다.

**아트 참고 이미지 45MB**는 저장소 대신 `.gitignore`로 보냈다 — 산출물은
`drawable-nodpi`의 시트로 이미 들어가 있어 원본을 함께 들고 다닐 이유가 없다.
죽은 코드(`InfoRow`, `displayLabel`)와 안 쓰는 임포트도 같이 지웠다.

**검증.** `SM_A165N` 1080×2340 실기기에서 시즌1(새 세이브)과 시즌2(용검 +24, 담금질
8회 누적) 두 상태를 각각 만들어 확인했다. 되살린 장치 둘을 넣고도 두 시즌 모두
**스크롤 없이 하단 다섯 메뉴까지 화면 안에 남는다** — 정보가 늘면 검 그림이 먼저
줄어드는 구조가 실기기에서 그대로 동작한다. 상점·조합소·보관함·도감도 함께 확인했고,
검증에 쓴 임시 세이브는 원래 값으로 되돌렸다.

### v3.0.0 — 2026-08-14 · 전설의 시대와 전면 시각·문구 개선

시즌 진행, 검·몬스터 원화, 전투 연출, 화면 문구를 한 묶음으로 다시 정리했다. 기존 세이브는
새 필드의 기본값과 보유 검 기록을 이용해 그대로 이어진다.

**세 시즌.** 시즌 I은 **불씨의 시대**, 용검 조합 뒤 시즌 II는 **심연의 시대**, 용검 +20
달성 뒤 시즌 III는 **전설의 시대**다. 시즌 I에서는 사냥과 관련된 검 스킬을 숨기고,
각 시즌 도움말에는 실제로 사용할 수 있는 규칙만 노출한다. 시즌 III 상점에는 전설 파괴
방지권을 추가했다. 골드 10,000,000 또는 조각 10,000으로 한 장을 사며, 전설 구간 파괴 시
원래 단계로 복구한다.

**검 원화.** 직검·곡도·대검·세검·마검·성검·용검은 +0~+20까지 단계마다 다른 원본을
사용한다. 전설 용검은 +21~+50까지 매 단계 별도 외형이며, 10단계마다 실루엣도 크게 바뀐다.
총 177개 강화검 외형을 원본 비율과 고품질 보간으로 표시해 날끝과 손잡이 잘림, 강제 도트화,
계열별 시트 혼용을 막았다. 검 이름도 7계열 147단계가 서로 겹치지 않게 분리했다.

**몬스터와 타격감.** 24구역 144종 몬스터를 고해상도 원화로 교체하고 가장자리의 흰 선과
잘림을 정리했다. 일반 타격·치명타·계열 공격용 전투 효과 16종, 스킬 배너, 피해 숫자와
타격 방향 연출을 추가했다. 보스 화면에서는 공격 효과가 얼굴을 가리지 않게 억제하고,
유료 재도전 선택은 제거했다.

**화면과 문장.** 검 중심 레이아웃, 하단 안전 영역, 메뉴 아이콘 정렬을 다시 맞췄다.
긴 설명은 핵심 규칙만 남겼고, 전투의 **검 스킬**과 영구 성장인 **대장 기술**을 구분했다.
파괴를 막지 못하고 실패 하락만 막는 수치는 모두 **하락 방지**로 바로잡았다. 설정의
라이선스 문구도 현재 실제로 표시되는 리소스를 기준으로 갱신했다.

**검증.** 순수 코틀린 도메인 테스트, 앱 단위 테스트, 디버그 APK 빌드를 함께 실행해
시즌 판정·전설 방지권·강화 복구·검 이름·이미지 매핑과 기존 세이브 호환을 확인했다.

### v3.0.1 — 2026-08-14 · 세이브 암호화와 변조 차단

평문 JSON이던 게임·도감·설정 세이브를 **AES-256-GCM 인증 암호문**으로 바꿨다. 파일마다
암호화 제공자가 12바이트 난수를 새로 만들고 파일명과 형식 버전을 인증 데이터에 묶어, 값 한 바이트 수정뿐
아니라 `collection.json`과 게임 세이브의 암호문을 서로 바꿔 끼우는 것도 거부한다.

암호키는 앱 파일에 저장하지 않고 **Android Keystore**에 만든다. 지원 기기에서는 StrongBox를
먼저 사용하고, 지원하지 않으면 일반 Android Keystore로 물러선다. 기존 설치는 이전 완료
표식이 없는 최초 실행에서만 평문 JSON을 읽는다. 현재 선택하지 않은 모드를 포함한 모든
게임·도감·설정 본 파일과 백업을 각각 검증해 암호화한 뒤 이전 창을 닫으며, 다음 실행부터
평문 세이브는 옛 형식으로 인정하지 않는다.

인증에 실패한 파일은 `.rejected`로 격리한다. 인증된 백업이 있으면 복구하고, 둘 다 실패하면
변조된 값을 사용하지 않은 채 안전한 초기 상태로 시작하며 화면에 이유를 알린다. 4MB를 넘는
비정상 저장 파일도 읽기 전에 차단한다.

클라우드 백업과 기기 간 전송은 Android 11 이하 규칙과 Android 12 이상 규칙에서 모두
명시적으로 제외했다. 오프라인 앱 특성상 루팅·실행 중 메모리 조작·정상 옛 암호문으로의
롤백까지 완전히 막지는 못하며, 배포판은 개인 릴리스 키로 서명해야 앱 개조 교체도 막을 수 있다.

### v3.0.2 — 2026-08-15 · 암호화 백업으로 기기 이전

설정에 **내보내기**와 **가져오기**를 추가했다. 내보내기 직전에 메모리의 최신
게임·도감·업적·통계·설정을 저장하고, 모든 모드를 하나의 `.sfgbackup` 파일로
묶는다. Android 시스템 파일 선택기를 쓰므로 저장소 권한이 필요 없고, 내 파일·퀵쉐어·
구글 드라이브 등 사용자가 고른 위치로 옮길 수 있다.

휴대용 백업 키는 비밀번호와 16바이트 난수를 PBKDF2-HMAC-SHA256 310,000회로
파생한다. 내용은 AES-256-GCM으로 암호화하며 비밀번호 오입력, 파일 손상,
허용되지 않은 파일명을 전부 쓰기 전에 검증한다. 검증과 새 기기 Keystore 암호화가
모두 끝난 뒤에만 현재 저장값을 교체한다.

비밀번호는 앱이나 백업 파일에 따로 저장하지 않는다. 잊으면 복원할 수 없으며,
서버가 없는 오프라인 게임이므로 정상 백업을 여러 번 불러오는 롤백까지는 완전히
차단할 수 없다.

### v3.0.3 — 2026-08-15 · 강화 터치 응답과 저장 안정성

세이브 암호화를 적용한 뒤 강화 버튼의 반응이 이전보다 무거워졌다. 강화 한 번마다
게임과 진행도를 UI 스레드에서 즉시 암호화하고 파일을 교체하면서 Android Keystore와
디스크 쓰기 시간이 터치 처리에 그대로 포함된 것이 원인이었다.

저장을 `Dispatchers.IO`의 단일 직렬 큐로 옮겼다. 강화 결과와 화면 상태는 먼저 갱신하고,
그 시점의 게임·진행도 스냅샷을 순서대로 저장한다. 단일 소비자가 처리하므로 느린 옛 저장이
최신 상태를 뒤늦게 덮지 않는다. 앱이 백그라운드로 가거나 백업·가져오기·초기화·종료를
준비할 때는 큐를 비워 최신 상태가 디스크에 확정된 뒤 다음 작업을 진행한다. Android
Keystore 키도 메모리에 보관해 같은 실행 중 반복 조회 비용을 줄였다.

개발 중 옛 디버그 APK를 다시 설치하면 Keystore의 이전 완료 표식은 남아 있는데 파일만
평문으로 되돌아가는 경우가 있었다. 배포 빌드는 기존처럼 평문을 엄격히 거부하고, 디버그
빌드에서만 이전 세이브를 다시 암호화할 수 있게 분리해 개발 중 진행도를 안전하게 복구한다.

**실기기 검증.** Galaxy A16에서 동일한 강화 동작을 다섯 번씩 측정했다. 동기 저장은
중앙값 24.35ms·최대 30.74ms였고, 직렬 저장 큐 적용 뒤에는 중앙값 1.80ms·최대 2.47ms로
줄었다. 암호화 백업 내보내기·가져오기 화면도 기기 테스트로 확인했다. Galaxy S20 Ultra에는
기존 데이터를 유지한 채 APK를 설치해 직검 +12 진행도가 그대로 열리고, 게임·도감·설정
세이브와 백업이 모두 인증 암호문으로 유지되는 것을 확인했다. 코어·앱 단위 테스트 783개,
린트, 디버그 APK와 기기 테스트 APK 빌드가 전부 통과했다.

검 흔들림과 강화 버튼의 성공·유지·하락·파괴 피드백은 그대로 남기되, 시스템 애니메이션
배율 대신 실제 프레임 시간을 기준으로 재생해 Galaxy A16과 S20 Ultra에서 같은 템포를
유지한다. 검 이미지 전체를 사각형으로 덮던 번쩍임은 제거했고, 실제 버튼이 눌리는 모션과
판정별 색 피드백을 버튼 안으로 옮겼다. 시도 번호로 연출을 구분해 같은 결과가 연속돼도 매번
재생하고, 다른 화면에서 돌아올 때는 지난 결과를 새 강화로 오인하지 않는다.

**상점과 스킬 규칙.** 강화석은 항상 4,000골드, 방지권·축복서·행운부적은 기존 기본가를
유지하도록 고정했다. 연속 구매 상승과 초기화 문구도 상점에서 제거했다. 전설 파괴 방지권의
골드 가격은 100,000,000골드로 조정했고 조각 가격은 10,000개를 유지했다. 기존 계열 스킬은
용검이 강화 구간별로 계승하도록 옮겼다.

| 용검 구간 | 계승 계열 | 스킬 |
|---|---|---|
| +1~+7 | 곡도 | 월영섬 |
| +8~+14 | 직검 | 일섬 |
| +15~+20 | 마검 | 흡혈 |
| +21~+27 | 세검 | 연속 찌르기 |
| +28~+34 | 대검 | 붕괴 |
| +35~+41 | 성검 | 심판 |
| +42 이상 | 용검 | 용의 숨결 |

용검을 제외한 검은 고강화여도 사냥 스킬을 표시하거나 발동하지 않는다. 용검의 화상 폭발과 펫
보조 피해도 사용자가 타격한 순간에만 합산하므로, 누르지 않았는데 몬스터 체력이 줄어들지
않는다.

**몬스터 원화와 타격 표시.** 원본 아틀라스를 동일한 격자로 잘라 팔·뿔·무기가 끊기던 구간은
전체 이미지의 피사체를 추적해 18종씩 분리하는 방식으로 재생성했다. 복잡한 실루엣은 분리된
부속 부품까지 같이 묶었고, 어비스 킹과 뒤틀린 고목은 전신 원화를 원본 자산으로 함께
보관한다. 게임에서는 몬스터 144종의 384×384 셀 전체를 84% 안전 영역에 비율을 유지해
표시하므로 외곽 흰선이나 석순 골렘의 팔 잘림을 막는다. 보스와 일반 몬스터 모두 타격 이펙트,
스킬명, 실제 총피해를 표시하고 한 방에 처치해 다음 몬스터가 나와도 직전 피해를 읽을 수 있다.

**앱 아이콘과 검증.** 선택한 1024픽셀 망치·검 원화를 적응형 런처 아이콘으로 적용하고
One UI 마스크에서 핵심 실루엣이 보이도록 안전 여백을 맞췄다. `:core:test`, `:app:testDebugUnitTest`,
`:app:lintDebug`, 디버그 APK·기기 테스트 APK 빌드가 모두 통과했다. Galaxy S20 Ultra와 A16에서
몬스터 144종의 원본 투명 경계와 실제 렌더링 프레임을 전수 검사했고, 잘림 회귀 대상 11종을
양쪽 실기기 스크린샷으로 다시 확인했다. 최종 APK도 두 기기에 설치해 정상 기동을 확인했다.

### v3.2.0 — 2026-08-17 · 13개 언어와 기기별 자동 선택

한국어·영어·일본어·중국어 간체·중국어 번체·스페인어·프랑스어·독일어·포르투갈어·
러시아어·태국어·베트남어·인도네시아어를 지원한다. 중국어 번체는 대만·홍콩·마카오의
기기 로케일을 함께 인식한다. 처음 실행하면 기기가 지원하는 언어를 자동으로 고르고,
지원하지 않는 언어에서는 영어를 사용한다. 설정의 **언어 변경**에서 기기 언어를 따르거나
13개 언어 중 하나를 직접 고를 수 있으며 선택값은 일반 설정과 암호화 백업에 함께 저장된다.

도메인 모델과 세이브에는 기존 한국어 식별자를 그대로 유지하고, Compose가 화면을 그리기
직전에 번역하는 구조를 넣었다. 그래서 이전 세이브와 도감·검 이름·업적 기록을 깨뜨리지
않으면서 모든 화면 텍스트와 토스트·접근성 설명·백업 파일명까지 같은 언어로 바뀐다.
숫자·강화 단계·몬스터 이름처럼 실행 중 조립되는 문장도 1,065개 고정 문구 조각을 긴 순서로
결합해 번역한다. 자주 표시되는 완성 문장은 즉시 찾고, 동적 문장은 첫 글자 인덱스와 LRU
캐시를 거치도록 해 강화와 사냥의 터치 경로에 번역 비용이 쌓이지 않게 했다.

Android 앱 언어 목록과 런처 이름도 지역별 리소스로 분리했다. 표시 언어는 13개지만 중국어
번체의 대만·홍콩 로케일을 따로 선언하므로 Android 로케일 항목은 14개다. 독일어처럼 길어지는
한 줄 버튼 문구는 글자 크기를 제한 범위 안에서 자동 조정해 메뉴 경계를 넘지 않는다.

검증에서는 12개 번역 카탈로그가 같은 키를 갖는지, 번역값에 한글이 남지 않는지, 실행 중
숫자를 붙인 문장까지 번역되는지, 모든 Compose 화면이 공통 번역 경로를 사용하는지를 자동으로
확인한다. Galaxy A16에서는 13개 언어의 설정 화면을 실제로 순회 렌더링하고 언어별 캡처를
남기는 기기 테스트를 추가했다.

### v3.3.0 — 2026-08-18 · 열세 언어 번역 정비와 출시 준비

번역을 전수로 다시 봤다. 실기기에서 열세 언어를 화면마다 눌러 보고, 사람 눈으로
놓치는 것은 검사 스크립트로 잡았다. 나온 것은 대부분 **문장을 조각으로 이어 붙인
자리**였다.

**어순.** 검 이름 대부분이 한국어 어순 그대로 낱말을 늘어놓은 꼴이었다. 스페인어
「Grieta Gran espada」, 프랑스어 「Rouillé Épée」처럼 수식어가 명사 앞에 붙었고,
포르투갈어 「Gyun-yeol」·러시아어 「Бёнся」·인도네시아어 「Nokseun」은 한국어 소리가
그대로 남아 있었다. 계열 이름을 한 곳에서 정하고 수식어 여든다섯 개를 붙일 꼴로 적어,
조합 이름 아흔다섯 개를 일곱 언어에서 다시 만들었다. 단계 이름으로 그때그때 만들어지는
이름 백아흔여섯 개도 짝을 미리 넣었다. 프랑스어 대검이 장검과 같은 「Épée longue」였던
것도 갈랐다.

**셈낱말.** 개(낱)가 개(dog)로 옮겨져 perro·chien·Hund·собака·狗·犬 가 됐다. 마리는
사람 이름 Marie·玛丽·マリ, 종(種)은 종(bell), 자루는 마대(sack), 초(秒)는 중국어에서
「第二個」(둘째)가 됐다. 숫자 자리가 뒤엣말에 달라붙어 「{}Die Entschädigung」으로
그려지던 곳도 열넷 있었다.

**동음이의.** 참(斬)이 charm 으로 읽혀 월광참이 「Mondschein-Charme」「月光魅力」가 됐고
일본어는 옮기지 못해 「ウォルガンチャム」로 소리만 남았다. 참격은 빗금 문자 「/」,
검사(劍士)는 검, 검증은 검+증, 수호상(像)은 상(賞), 천공(天空)은 穿孔, 전설 파괴 시의
시(時)는 city, 심판은 운동경기 심판, 분쇄는 중국어에서 짝사랑(暗恋)이 됐다. 백업
내보내기·가져오기는 항만 수출입(出口·进口)이었다.

**한자권 빈칸.** 일본어와 중국어는 낱말을 띄어 쓰지 않는데 조각 사이 빈칸이 남아
「亀裂 大剣」처럼 나왔다. 세 언어에서 사백일흔다섯 자리를 지웠다.

**숫자 단위.** 만·억·조를 한글 글자 그대로 코드에 박아 두어 중국어·일본어 화면에도
한글이 섞여 나왔다. 단위 글자를 언어마다 두었다 — `GameLanguage.myriadUnits`.

**말투.** 새로 쓴 문장은 반말인데 옛 문장은 높임말이라 한 화면에 두 말투가 섞였다.
독일어 Sie/du, 프랑스어 vous/tu, 러시아어 вы/ты 를 반말로 맞췄다.

**화면 넘침.** 사냥터 몬스터 목록이 「클리어」 배지와 붙어 읽히던 것, 상점 물건 설명이
값 단추에 맞닿던 것, 무한 회랑의 확정·미확정 줄이 서로 맞붙던 것, 아래 단추 줄에서
프랑스어 「Terrains de chasse」가 두 줄로 넘치던 것을 고쳤다.

정수 요구 줄은 힌트 문장과 한 덩어리로 묶여 있어 사전에 통째로 없었다. 줄을 따로 떼어
구역 스물네 곳의 자리가 그대로 쓰이게 했다. 조합식과 계열 조합 칸도 계열 이름에서
짜 맞추게 바꿔, 이름을 고치면 문구가 따라오게 했다.

**검사 도구.** 같은 실수를 다시 하지 않도록 생성기 다섯과 검사기 여섯을
`tools/i18n/` 에 두었다. 한자 사이 빈칸·숫자 붙음·이름 중복·조각 이어 붙임은
0이어야 하고, 한국어 소리 잔존과 문장 가운데 큰 글자는 목록을 눈으로 본다.
사전 열둘이 키 1,368개로 같고 값에 한글이 남지 않은 것을 빌드에서 확인한다.

**출시 준비.** 릴리스 빌드를 만들어 실기기에서 한 판 했다. 축소 과정에서 사전 열두
파일과 배경음 두 곡이 그대로 남는 것을 APK 안에서 확인했다. 서명 키는 다른 앱들과
같은 공용 업로드 키로 바꿨다(첫 출시라 지금이 아니면 못 바꾼다). 스토어 아이콘
512×512, 그래픽 이미지 1024×500, 열세 언어 스크린샷 일흔여덟 장을 만들었고,
등록정보 문안은 열네 언어로 `legal` 저장소에 두었다 — 앱 저장소가 비공개가 되어도
스토어 링크는 열려 있어야 하기 때문이다.

### 코드 규칙

- **`:core`는 순수 코틀린이다.** 안드로이드 API를 넣지 말 것. 도메인이 기기 없이
  JVM에서 테스트되는 것이 이 프로젝트의 뼈대다
- **난수는 주입한다.** `ForgeEngine.attempt(state, items, rng)`처럼 밖에서 받는다.
  난수 소비 순서는 테스트가 의존하는 계약이다 (1: 성공 판정, 2: 파괴/하락 판정)
- **UI 텍스트는 전부 한국어**
- **주석은 "왜"를 적는다.** 무엇을 하는지는 코드가 말한다. 되돌린 시도와 그
  이유가 남아 있어야 같은 실수를 반복하지 않는다
- **세이브 필드를 더할 때는 반드시 기본값을 준다.** `@Serializable` 데이터
  클래스에 기본값이 없으면 옛 세이브가 열리지 않는다
- **커밋 메시지와 문서는 구현 내용과 판단 근거만 기록한다**

### 번역 — 문장은 통째로 넣는다

번역은 **한국어 원문이 곧 키**다 (`app/src/main/assets/i18n/*.json`).
`GameTranslator.translate()` 는 완성 문장 → 숫자만 `{}` 로 바꾼 꼴 → **조각 이어 붙이기**
순으로 찾는데, 마지막으로 흘러가면 뜻이 깨진다. 어순이 뒤집히고(「Grieta Gran espada」),
한자권은 낱말 사이에 빈칸이 남는다(「亀裂 大剣」).

- **화면에서 이어 붙여 만드는 문장은 나올 수 있는 짝을 미리 다 키로 넣는다.**
  계열 이름·단계 이름·구역 정수·조합식은 `tools/i18n/` 의 생성기가 만든다
- **셈낱말을 조심한다** — 개·마리·종·자루·회·초·장은 기계 번역이 거의 틀린다
  (개→dog, 마리→Marie, 종→bell, 자루→sack)
- **숫자 단위는 번역이 아니라 코드가 만든다** — `GameLanguage.myriadUnits`
- **말투는 반말로 통일한다** — 독일어 du, 프랑스어 tu, 러시아어 ты
- 고친 뒤 `tools/i18n/` 의 검사기를 돌린다. 한자 사이 빈칸·숫자 붙음·이름 중복·조각
  이어 붙임은 **0이 아니면 버그**다

- **런처 이름은 앱 안 언어 선택을 따르지 않는다.** `values-*/strings.xml` 의
  `app_name` 은 **기기 로케일**로 뽑히므로, 폰이 영어인데 앱에서 일본어를 골라도
  홈 화면에는 `Sword Forge` 가 뜬다. `localeConfig` 를 선언해 두어 안드로이드 13
  이상의 시스템 설정 → 앱 → 언어로 바꾸면 이름까지 같이 바뀐다. 앱 안 선택까지
  반영하려면 `AppCompatDelegate.setApplicationLocales` 를 붙여야 한다

자세한 것은 [`tools/i18n/README.md`](tools/i18n/README.md).

### 아트 규칙 — 협상 대상이 아님

**타사 상용 게임의 저작물을 절대 쓰지 않는다.** 스프라이트를 새로 넣어야
한다면 사용 권한을 확인하고, 외부 리소스는 출처와 라이선스를 앱 설정 화면의 표기에
추가한다. 현재 강화검·몬스터·전투 효과는 프로젝트 전용 제작이고, 고유검·펫 일부만
CC0 보조 스프라이트와 배경음 두 곡을 사용한다. 효과음은 코드로 합성한다.

### 알아 두면 시간을 아끼는 함정

- **사냥 ViewModel 테스트는 단언을 전부 `leaveHunt()` 뒤에 둔다.** 앞에 두면
  실패 예외가 `leaveHunt()`를 건너뛰어 1초짜리 사냥 루프가 가상 시간에서
  영원히 돌고, 빌드가 40분씩 멈춘다
- **빌드 성공 ≠ 동작 확인.** 테스트가 전부 통과해도 화면이 판정과 다른 조건을
  보고 있으면 버튼이 아예 없는 채로 출시된다. 실기기 한 판이 테스트 500건보다
  빠르게 잡는 것이 있다
- **파괴창이 열려 있으면 강화가 막힌다** (`pendingDestroy != null` → `canRoll` false).
  루프를 도는 테스트는 매 시도 뒤 `ForgeEngine.confirmDestroy()`로 창을 흘려보내야 한다
- **화면을 통째로 다시 짤 때는 「호출이 딸려 나갔는지」를 따로 본다.** 죽은 코드는
  컴파일러가 잡지만 **죽은 호출은 아무도 안 잡는다** — 정의가 남아 있으면 빌드도
  테스트도 통과한다. v2.9 개편에서 담금질 게이지와 보너스 합계 줄이 이렇게 사라졌다.
  화면 개편 뒤에는 **개편 전 스크린샷과 나란히 놓고 없어진 요소를 세어 보는 것**이
  가장 빠르다

### 지금 열려 있는 것

- **도감을 채우면 진짜 파괴 확률이 줄어들게 하기** — 논의만 되고 구현 전이다.
  지금은 어떤 보너스도 파괴를 막지 못하고(방지권만 사후에 되살린다) `dropGuard`는
  "파괴를 면한 실패"의 하락만 붙든다. 파괴 자체를 깎으려면 `ForgeOdds`·
  `ForgeEngine`·`BalanceSimulation` 셋을 함께 움직여야 한다
- **펫 설명과 몬스터 이름의 결** — 뜻은 맞지만 열세 언어 모두가 손으로 다듬은
  문장은 아니다. 원어민이 읽으면 더 자연스럽게 고칠 자리가 남아 있다

```bash
./gradlew :app:assembleDebug
```

밸런스 리포트만 보려면:

```bash
./gradlew :core:test --tests "com.geomgang.core.sim.BalanceSimulationTest"
```

```
sdk.dir=C\:\\Users\\<사용자>\\AppData\\Local\\Android\\Sdk
```

## 출시 준비

절차와 콘솔에 답할 것은 [`store/출시-체크리스트.md`](store/출시-체크리스트.md) 에 있다.
여기에는 배경만 적는다.

### 릴리스 빌드

```bash
./gradlew :app:bundleRelease :app:assembleRelease
```

- 스토어에 올리는 것은 **AAB** — `app/build/outputs/bundle/release/app-release.aab`
- 실기기 확인용은 APK — `app/build/outputs/apk/release/app-release.apk`

코드 축소와 리소스 축소가 켜져 있어 디버그 빌드보다 훨씬 작다.
`kotlinx-serialization` 이 세이브를 읽지 못하는 일이 없도록 ProGuard 규칙에
도메인 클래스의 serializer 와 enum 이름을 보존해 두었다.

> **축소가 무엇을 지웠는지 확인한다.** 이 프로젝트는 리소스 축소를 켜 두었고,
> 번역 사전은 `assets/` 라 축소 대상이 아니지만 배경음은 `res/raw/` 다.
> 올리기 전에 APK 안을 열어 사전 열두 파일과 소리 두 개가 남아 있는지 본다
> (축소가 이름을 `res/Qv.ogg` 처럼 바꾸므로 확장자로 찾는다).

### 서명 — 공용 업로드 키

**삐약푸쉬·왁뿌볼·끝말잇기와 같은 업로드 키를 쓴다.** 앱마다 키가 갈라지면
나중에 관리가 안 된다.

- 키 파일 `upload.jks` (별칭 `wordchain`), 비밀번호는 `keystore.properties`
- 둘 다 `.gitignore` 에 있어 저장소에 올라가지 않는다
- 원본 백업은 `C:\workAndroid\_서명키_백업\`
- 인증서 SHA-1 `D7:9A:58:0B:56:B2:34:E3:6F:A4:18:0E:B5:90:2A:EF:DF:B7:68:1F`
- AAB 안에 `META-INF/WORDCHAI.RSA` 가 보이면 이 키로 서명된 것이다

`keystore.properties` 가 없으면 릴리스를 서명하지 않는다. 공개된 디버그 키로
배포하면 같은 키로 서명한 개조 APK 가 업데이트될 수 있어 세이브 보호가 약해지므로
의도적으로 대체 서명을 하지 않는다.

> **키를 잃어버리면 같은 패키지명으로 다시는 업데이트를 올릴 수 없다.**

### v3.4.1 — 2026-09-22 · 전면·보상형 광고와 광고 자리 정하기

애드몹 계정을 만들어 진짜 ID 를 넣고, 배너 하나이던 것을 셋으로 늘렸다.
**테스트 통과, 사전 열두 벌 1,369키로 같음.**

**어디에 띄우느냐가 설계의 전부였다**

광고를 붙이는 일은 SDK 를 부르는 것이 아니라 **게임의 어느 순간을 팔 것인지**
고르는 일이다. 세 자리를 이렇게 정했다.

| 형식 | 자리 | 왜 거기인가 |
|---|---|---|
| 배너 | 대장간 화면 아래 | 손이 멈춰 있는 화면. 사냥터·회랑에는 안 띄운다 |
| 전면 | 사냥터·회랑에서 나올 때 | 한 판이 끝난 매듭이고 화면이 바뀌는 자리다 |
| 보상형 | 자리비움 보상 두 배 | 안 봐도 손해가 없고, 봐도 게임이 안 망가진다 |

**게임의 균형은 팔지 않았다.** 강화 성공률·파괴 복구에 보상형을 붙이면 당장
수익은 오르지만, 그 순간 이 게임은 강화 게임이 아니라 광고를 보는 게임이 된다.
자리비움 보상은 원래 «켤 이유»로 만든 덤이라 두 배가 되어도 사냥터가 죽지 않는다.

**전면 광고는 빈도가 전부다**

나올 때마다 띄우면 사냥을 두 번 다녀온 사람이 광고를 두 번 본다. 그러면
사냥터를 안 간다. 켠 뒤 3분, 그리고 한 번 뜬 뒤 4분으로 묶었다. 광고가 아직
안 받아졌으면 **기다리지 않고 그냥 넘어간다** — 화면 전환이 멈추면 게임이
느린 것으로 읽힌다.

띄울 자리는 나가는 길목마다 심지 않고 **화면 전환 자체를 봤다.** 사냥터에서
나오는 길은 뒤로 가기·나가기·포기·회랑 진입으로 넷인데, 길목마다 코드를 심으면
새 길이 생긴 날 반드시 하나를 빠뜨린다. `overlay` 가 Hunt·Gauntlet 에서 None
으로 바뀌는 것만 보면 어느 길로 나오든 한 번 걸린다.

**문구 하나가 열두 파일이다**

보상형에는 단추 문구가 필요했다 — 배너에는 없던 일이다. 「광고 보고 두 배로」
하나를 넣으려고 사전 열두 벌을 함께 고쳤다. `LocalizationCatalogTest` 가 키
집합이 어긋나면 빌드를 막으므로 빠뜨릴 수는 없다.

문장은 **통째로** 키에 넣었다. 「광고」와 「두 배로」를 따로 두면 조각 이어
붙이기로 흘러 어순이 뒤집힌다 — 이 프로젝트가 열세 언어에서 이미 겪은 일이다.

**두 배를 받았는지 보이게**

보상을 두 배로 줄 때 골드만 늘리면 무엇이 일어났는지 알 수 없다. 창에 뜬
숫자를 그 자리에서 두 배로 바꿨다. 새 문구 없이 피드백을 만든 방법이다.
단추는 한 번 누르면 사라지고, 띄울 광고가 없으면 **처음부터 그리지 않는다.**

**아직 안 한 것**

실기기 확인. 폰이 붙어 있지 않아 배너·전면·보상형 **어느 것도 실제로 뜨는
것을 보지 못했다.** 빌드가 통과했다고 화면이 맞는다는 보장이 없다는 것은 이
프로젝트가 이미 여러 번 겪었다. 특히 전면 광고는 3분 조건 때문에 켜자마자
확인되지 않으니, 사냥을 한 판 다녀오는 식으로 봐야 한다.
