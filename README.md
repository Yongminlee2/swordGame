## 게임 소개

검을 강화한다. 성공하면 단계가 오르고, 실패하면 그대로거나, 떨어지거나, 부서진다.
부서진 검에서 조각을 주워 방지권을 만들고, 그 방지권으로 다음 검을 살린다.
그렇게 +20까지 올리는 것이 목표다.

2000년대 국내 플래시 게임에서 유행했던 "검 강화하기" 장르를 안드로이드로 재해석한 것이다.
게임 시스템의 뼈대(강화 · 방지권 · 줍기 · 조합소)는 그 장르의 관습을 따르되,
코드 · 그래픽 · 사운드 · 밸런스는 전부 새로 만든다.

## 설계 방향

이 프로젝트를 관통하는 원칙 다섯 가지.

### 1. 게임 규칙은 안드로이드를 몰라야 한다

강화 판정 · 확률표 · 경제 · 진행도 규칙을 `:core`라는 **순수 Kotlin 모듈**에 격리한다.
안드로이드 의존성이 들어오면 컴파일이 깨지도록 모듈 자체를 `java-library`로 둔다.

이렇게 하면 두 가지를 얻는다. 게임 규칙을 화면과 무관하게 이해하고 수정할 수 있고,
JVM 단위 테스트가 빠르게 돌아 **10만 판 밸런스 시뮬레이션을 테스트로 돌릴 수 있다.**

### 2. 난수는 주입한다

강화 엔진은 `Random`을 파라미터로 받는다.

```kotlin
fun attempt(state: GameState, items: UsedItems, rng: Random): ForgeResult
```

시드를 고정하면 "이 상태에서 이 난수면 반드시 파괴"를 테스트로 검증할 수 있다.
확률 게임에서 이 장치가 없으면 밸런스 버그를 재현조차 못 한다.
전역 난수를 쓰는 순간 이 게임은 디버깅이 불가능해진다.

### 3. 밸런스는 감이 아니라 시뮬레이션으로 잡는다

확률표를 건드릴 때마다 10만 판을 자동 플레이해서
**평균 도달 단계 · 파산율 · +20 달성률**을 숫자로 확인한다.
"체감상 좀 어려운 것 같은데" 로 조정하지 않는다.
이 시뮬레이션은 튜닝 도구인 동시에 회귀 방지선이다.

### 4. 손맛을 깎는 편의 기능은 넣지 않는다

- 방지권 자동 사용은 **기본 꺼짐**. 설정에서만 켤 수 있다.
  파괴 순간 2.5초 안에 원을 눌러야 하고, 놓치면 검이 날아간다.
  "아 눌렀어야 했는데"가 이 게임의 핵심 감정이다.
- 자동 강화는 **안전구간(+0~+4)에서만** 동작한다.
  하락·파괴가 걸린 구간을 자동화하면 게임이 남지 않는다.

### 5. 진행이 막히는 상태를 만들지 않는다

골드가 0이 되어도 조각이라는 별도 화폐로 재기할 수 있다.
검 · 골드 · 조각이 전부 바닥나면 골드를 300으로 채워 준다.
검을 사고 되파는 순환은 한 바퀴에 40골드씩 손해이고 구제 상한이 300이므로,
이 장치로 의미 있는 골드를 벌 수는 없다.

## 핵심 시스템

### 강화 판정

```
강화 버튼 → 비용 차감 → 성공 판정
                          ├ 성공 → 단계 +1
                          └ 실패 → 구간별 처리
                                    ├ +1~+5   : 유지 (안전구간)
                                    ├ +6~+12  : 1단계 하락
                                    └ +13~+20 : 파괴 판정 → 파괴 or 하락
```

성공률은 +1의 95%에서 시작해 +20의 2%까지 떨어진다.
파괴 구간에서 실패하면 단계에 따라 40~80% 확률로 파괴된다.

### 난이도

기준 확률표 **한 벌**에 배수를 곱해 네 모드를 만든다. 표를 여러 벌 관리하지 않는다.

| 모드 | 배수 | 상한 |
|---|---|---|
| 쉬움 | ×1.25 (98% 상한) | +20 |
| 일반 | ×1.00 | +20 |
| 지옥 | ×0.75 | +20 |
| 무한 | ×1.00, +21부터 직전의 85%씩 감쇠 (하한 0.5%) | 없음 |

무한 모드는 실패하면 무조건 파괴다.

각 모드는 골드 · 아이템 · 기록이 완전히 분리된 독립 세이브를 갖는다.

### 방지권과 줍기

파괴 판정이 나오면 작은 원이 뜬다. **2.5초** 안에 누르면 방지권을 태워 검을 살린다.
살리지 못했다면 파편이 흩어진다. **3초** 안에 누르면 조각을 회수한다.
조각은 조합소에서 방지권 · 축복서 · 행운부적 · 상위 검으로 바꾼다.

### 무기 — 계열 8종 × 티어 11종

| 계열 | 해금 |
|---|---|
| 직검 · 곡도 · 대검 · 세검 | 기본 |
| 쌍검 | +12 달성 |
| 마검 | 파괴 50회 |
| 성검 | +15 달성 |
| 용검 | +18 달성 |

티어는 강화 단계에 따라 자동 결정된다.
녹슨 검(+0~2) → 강철검 → 은장검 → 룬검 → 화염검 → 뇌전검 → 여명의 성검 → 흑룡참(+19~20).
무한 모드에는 용린참 · 심연검 · 이름 없는 검이 추가된다.

**총 88종**이며 전부 도감 수집 대상이다.
검은 날 · 코등이 · 손잡이 · 보석 · 오라 5개 레이어를 겹쳐 그리므로,
새 계열을 추가할 때 날 실루엣만 그리면 되고 코드는 건드리지 않는다.

### 통계 화면

이 게임에서 가장 신경 쓴 화면.
단계별로 **"표기 40% / 실제 37.2% (241회)"** 를 나란히 보여준다.
강화 게임 플레이어가 늘 품는 확률 조작 의심을 데이터로 직접 해소시키는 것이 목적이다.

## 기술 스택과 구조

| 항목 | 선택 |
|---|---|
| 언어 | Kotlin |
| UI | Jetpack Compose |
| 최소 SDK | 26 |
| 대상 SDK | 36 |
| 직렬화 | kotlinx-serialization (JSON) |
| 저장 | 앱 내부 저장소 파일 |
| 방향 | 세로 고정 |
| 네트워크 | 없음 (완전 오프라인) |

### 모듈

```
:core   순수 Kotlin. 안드로이드 의존성 없음. 게임 규칙 전부.
:app    Compose UI · ViewModel · 저장소 구현.
```

### 의존 방향

```
ui (Compose)  →  viewmodel  →  domain (:core)  ←  data
```

역방향 의존은 없다. `data`는 도메인 상태를 직렬화할 뿐 규칙을 갖지 않는다.

### :core 구성

| 파일 | 책임 |
|---|---|
| `GameState.kt` | 한 모드의 전체 상태 (불변 data class) |
| `ForgeEngine.kt` | 강화 1회 판정. 순수 함수, 난수 주입 |
| `RateTable.kt` | 난이도별 · 단계별 확률 데이터 |
| `Economy.kt` | 강화 비용, 판매가, 파산 구제 판정 |
| `Recipes.kt` | 조합소 교환식, 상점 가격 |
| `WeaponCatalog.kt` | 계열 × 티어 정의, 단계 → 티어 매핑 |
| `Progress.kt` | 도감 · 업적 · 칭호 · 통계 누적 규칙 |

### 저장 안전성

자동 저장은 매 강화마다 일어난다. 그래서 중단 타이밍이 많다.

1. 임시 파일에 쓴다
2. 기존 파일을 `.bak`으로 옮긴다
3. 임시 파일을 정식 이름으로 rename 한다

읽기 실패 시 `.bak`으로 폴백하고, 둘 다 깨졌으면 그 파일만 초기화한다.
모드별로 파일이 분리되어 있어 한 모드가 깨져도 나머지와 도감은 살아남는다.

**강제 종료 악용 차단**: 방지권 원이 떠 있는 2.5초 동안 앱을 죽이면
파괴를 무효화할 수 있다. 그래서 판정 결과가 나오는 즉시 "파괴 대기" 상태로 저장하고,
앱을 다시 켜면 파괴 확정으로 처리한다. 방지권 기회는 그 자리에서만 유효하다.
이 처리가 없으면 고단계 구간이 통째로 무의미해진다.

## 저작권 및 리소스 방침

출시를 염두에 두고 처음부터 안전하게 관리한다.

**사용하지 않는 것**

- 원작 플래시 게임(SWF)에서 추출한 그래픽 · 사운드 · 데이터
- 타사 상용 게임의 무기 이미지 — **변형해서 쓰는 것도 하지 않는다.**
  변형해도 원본을 식별할 수 있으면 2차적저작물로 침해가 된다.

**사용하는 것**

- 자체 제작 벡터 드로어블
- CC0 / 퍼블릭도메인 에셋
- 표기 조건을 지킨 CC-BY 에셋 — 설정에 라이선스 고지 화면을 둔다

"용 모티프 곡선날", "화염 오라", "날개형 코등이" 같은 판타지 무기의 일반적 표현 관습은
특정 주체의 저작물이 아니므로 자유롭게 사용한다.

## 개발 일지

### v0.1.0 — 2026-07-26 · 기획 및 설계 확정

프로젝트 시작. 코드는 아직 없고 설계 문서만 있는 단계.

**결정한 것들**

| 항목 | 결정 | 근거 |
|---|---|---|
| 강화 상한 | 구간형 +20 | 상한이 있어야 "클리어" 감각이 생긴다. 도감 · 수집을 넣으려면 20단계 정도의 여유가 필요했다 |
| 모드 구성 | 난이도 3종 + 무한 | 확률표 한 벌에 배수만 곱하면 되니 구현 비용 대비 수명이 길다 |
| UI 스택 | Jetpack Compose | 화면 7~8개가 전부 "상태 → 화면" 형태이고 연출이 많다. View + XML 대비 배선 코드가 크게 줄어든다 |
| 도메인 격리 | `:core` 별도 Gradle 모듈 | 안드로이드 의존성 유입을 컴파일 단계에서 차단. JVM 테스트가 빨라져 대량 시뮬레이션이 가능해진다 |
| 무기 구조 | 계열 8종 × 티어 11종 = 88종 | 단순 단계별 외형 변화만으로는 수집 콘텐츠가 금방 바닥난다 |
| 계열 선택 | 기본 검 구매 시 직접 선택 | 무작위 배정이면 도감 빈칸을 의도적으로 채울 수 없어 답답하다 |
| 아트 조달 | 벡터 5레이어 조립 + CC0 에셋 | 88종을 통 이미지로 그리면 관리가 불가능하다. 레이어 조립이면 날 실루엣만 늘리면 된다 |

**원작과 의도적으로 다르게 간 부분**

- **모드를 초기화해도 도감 · 업적은 남긴다.**
  수집물이 초기화로 날아가면 아무도 초기화를 누르지 않게 되고,
  그러면 재도전이라는 이 장르의 핵심 재미가 막힌다.
- **자동 강화를 안전구간으로 제한한다.**
  전 구간 자동화는 편하지만 게임을 지운다.
- **불운형 업적을 넣는다.**
  "10연속 실패", "+19에서 파괴" 같은 것들.
  망했을 때도 얻는 게 있어야 다시 시작하게 된다.

**설계 문서 셀프 리뷰에서 잡은 구멍 2건**

문서를 다 쓰고 다시 읽으면서 발견한 것들.

1. **검을 잃은 뒤 새 검의 출처가 문서에 없었다.**
   파괴되면 검이 사라지는데 다음 검을 어떻게 얻는지가 정의되어 있지 않았다.
   무료 지급으로 두면 "파산"이라는 상태가 성립하지 않고,
   파산 구제 조항도 조합소의 `+5 검 교환`도 전부 의미를 잃는다.
   → **기본 검 = 상점 100골드**로 확정하고 파산 구제 조건을 그 가격 기준으로 재정의.
   계열 선택 시점도 이 구매 시점으로 확정.

2. **마검 해금 조건이 존재하지 않는 업적을 참조하고 있었다.**
   해금 조건은 "파괴 50회 업적"인데 업적 목록에는 파괴 100회밖에 없었다.
   → 업적 목록에 파괴 50회 추가.

3. **파산 구제가 무한 루프를 만들 수 있었다.** (구현 계획을 쓰다가 발견)
   구제로 검 한 자루만 주면 골드가 0이라 강화 비용 30조차 못 낸다.
   그렇다고 그 검을 팔면(60골드) 다시 검이 없어져 구제가 재발동한다.
   → 구제 지급을 **검이 아니라 "골드를 300으로 채우기"** 로 변경.
   검은 상점에서 직접 사게 해서 계열 선택권도 지킨다.
   사고 되파는 순환은 한 바퀴에 40골드 손해이고 구제 상한이 300이라 악용 가치가 없다.

그 외 두 가지로 읽힐 수 있던 곳들을 하나로 확정:
축복서 +10%p의 적용 순서(난이도 배수 뒤에 가산, 98% 상한),
비용/판매가 표의 열이 목표 단계인지 보유 단계인지,
자동 강화가 정확히 어느 단계에서 멈추는지(+0~+4에서만 시도).

## 빌드 방법

```bash
./gradlew assembleDebug
```

산출물: `app/build/outputs/apk/debug/app-debug.apk`

테스트만 돌리려면 (도메인 로직은 전부 JVM 테스트라 기기 없이 실행된다):

```bash
./gradlew :core:test
```

> 아직 M1 이전이라 Gradle 프로젝트가 생성되지 않았다. 위 명령은 M1 완료 후 동작한다.
